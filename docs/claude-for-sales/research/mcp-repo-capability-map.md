## 1. Capability Map — What This Connector Does Today

**Architecture** (`README.md:7-19`, `src/server.py:1-30`): a Python **FastMCP v3** server that (a) spawns **one** `@playwright/mcp` subprocess via `npx` over stdio and proxies its ~70 primitives under a `playwright_*` prefix, and (b) layers 19 hand-written `web_*` orchestration tools on top. Deployed to Railway over Streamable HTTP; also runs locally (`uv run python src/server.py`) or via Docker.

**Tool surface** (`README.md:25-56`, confirmed against `src/tools/*.py` and `src/server.py:163-232`):

| Category | Tools | Source |
|---|---|---|
| Navigation | `web_navigate_and_wait`, `web_wait_for_ready`, `web_discover_navigation` | `src/tools/navigation.py` |
| Extraction | `web_extract_table` (rows/csv/markdown, DOM or snapshot mode), `web_extract_page_data`, `web_extract_links`, `web_extract_article`, `web_extract_metadata`, `web_extract_structured_data` (CSS-selector map, no LLM parsing needed) | `src/tools/extraction.py`, `src/tools/content.py` |
| Forms | `web_discover_form` (W3C accessible-name resolution + HubSpot/Marketo/MUI/Bootstrap/Gravity Forms heuristics, `src/tools/forms.py:29-80`), `web_fill_form` | `src/tools/forms.py` |
| Search | `web_search`, `web_search_and_extract` — engine choice of `duckduckgo` (HTML-lite)/`bing`/`google`, **default is now `bing`** (`src/tools/search.py:15-16`) | `src/tools/search.py` |
| Auth/session | `web_login` (auto-fill), `web_check_auth_state`, `web_save_session`/`web_load_session` (cookies + localStorage, best-effort — httpOnly cookies unreachable via JS) | `src/tools/auth.py`, `src/tools/session.py` |
| Scripting/perf | `web_execute_js`, `web_save_pdf`, `web_performance`, `web_accessibility_audit` | `src/tools/scripting.py`, `src/tools/performance.py` |
| Playwright primitives | All 70+ `@playwright/mcp` tools, `playwright_` prefix, plus 2 hand-rolled wrappers (`playwright_navigate`, `browser_wait_for`) for parameter-mapping bugs upstream | `src/server.py:178-232` |

**Deployment / auth** (`README.md:58-90`, `railway.json`, `Dockerfile`):
- Railway via Dockerfile, `startCommand: uv run python src/server.py`, `restartPolicyType: ON_FAILURE` (max 3 retries), `/health` check. **No `numReplicas` set** — single instance unless changed in the Railway dashboard (not visible from repo).
- OAuth 2.1 is **wired but optional and currently unconfigured by default** — `create_oauth_proxy()` returns `None` unless `OAUTH_CLIENT_ID` is set (`src/auth.py:8-15`). The FastMCP enhancements doc (`docs/fastmcp-enhancements-guide.md:443-503`) lists "OAuth activation" as a **P1, not-yet-shipped** item — meaning as of this read, the connector is effectively **anonymous/shared access**, not per-CSM-identified, unless someone has since turned it on in Railway env vars (can't confirm from the repo).
- Anti-bot posture: `--headless --no-sandbox`, an injected `stealth.js` init-script, a spoofed desktop Chrome UA, and 1366×768 viewport are baked into every browser launch (`src/providers/playwright_subprocess.py:21-37`). Optional residential-proxy env vars (`PLAYWRIGHT_PROXY_SERVER/_USER/_PASS`) exist but are unset by default (`.env.example:16-19`).

**Known constraint — CAPTCHA/bot-detection from Railway IPs** (this is explicitly documented, not inferred):
- `docs/fastmcp-enhancements-guide.md` and `ROADMAP.md:44` both state Google/DuckDuckGo are unreliable from server environments; Bing is now the default engine specifically because of this.
- The dev team's own research (`.claude/cache/agents/oracle/output-20260327-stealth-research.md:6,46-48`) is blunt: **"Railway datacenter IPs are pre-flagged by anti-bot systems... residential proxy mandatory for Google."** Their own priority order was DDG HTML-lite > Bing > SearXNG sidecar > Exa API — i.e. even the people who built this don't fully trust browser-based Google search from this box, and no SearXNG/Exa fallback is implemented yet.

## 2. What Ships in `skills/` — and the EBR Relationship

Only **one skill exists in this repo today**: `skills/browser-automation/SKILL.md` (79 lines). It is a **generic tool-usage guide** — navigation, extraction, forms, search, error recovery, anti-patterns — with zero business-domain content (no EBR, no Fourth-specific workflow, no sales language). Confirmed by grep: `ebr|prospect|sales|salesforce|account.plan` inside `src/`, `skills/`, `docs/`, `README.md`, `ROADMAP.md` returns **only forward-looking references in the FastMCP enhancements doc and ROADMAP history** — no actual sales/EBR code or skill content lives here.

**Why**: `ROADMAP.md:55-61` documents a deliberate 2026-03-27 decision to **delete** `skills/fourth-workflows/` (which held "Fourth login/module/extraction recipes") and rebuild this repo as a **general-purpose** web-automation connector. The EBR-specific orchestrator + "playwright-competition" research skill your background references is a **downstream consumer** — it lives in whichever repo hosts the CS Claude Project, not here. `ROADMAP.md:39-44` ("Rewrite EBR Project Instructions + Orchestrator Skill," 2026-03-31) confirms the EBR skill was rewritten specifically to **point at this connector by name** ("browser research uses `fourth-playwright` MCP connector with Bing as default search engine") rather than to embed its own scraping logic.

**Implication for the sales reuse plan**: this repo is the right foundation (proven, hardened, already stealth/anti-bot-tuned), but there is **no existing sales-flavored skill to copy** — the "hone `skills/browser-automation`" work in deliverable #4 means *authoring a new skill* (e.g. `skills/account-research/SKILL.md`) that layers a curated hospitality-prospect source list and sales-research workflow on top of the existing generic tools, the same way the (separate) EBR orchestrator skill layers a customer-research workflow on top.

## 4. Risks of Live Use at SKO (Room Full of Reps) + Mitigations

| Risk | Why it's real (evidence) | Mitigation |
|---|---|---|
| **Single shared browser instance = collision risk.** `mount_playwright()` spawns exactly **one** `@playwright/mcp` subprocess at server-mount time (`src/providers/playwright_subprocess.py:58-81`, called once from `src/server.py:158`). There is no per-session browser-context pooling anywhere in the codebase. If Railway runs 1 replica (the default per `railway.json`, which sets no `numReplicas`), **every rep in the room is driving the same headless Chrome tab.** Rep A's `web_navigate_and_wait` mid-competition could yank the page out from under Rep B's `web_extract_article` call. | **Before SKO: verify Railway's actual replica count and, ideally, load-test with 10-30 concurrent tool calls to see whether requests serialize gracefully or genuinely stomp on each other.** If it's truly one shared browser, either (a) scale Railway to N replicas with sticky routing so each rep effectively gets an isolated browser, or (b) restructure the competition so reps run research **sequentially/staggered** rather than all-at-once, or (c) accept degraded reliability and message it as "expect occasional retries" rather than a flawless demo. |
| **In-memory, per-process session store with no user scoping.** `_session_store: dict[str, dict] = {}` is a **global module-level dict** (`src/tools/session.py:11`) keyed by `session_name` (default `"default"`), not by user identity. Two reps both calling `web_save_session()` with the default name will **silently overwrite each other's saved cookies/localStorage.** Sessions also vanish on any Railway redeploy. | Have each rep pass a **unique `session_name`** (e.g. their initials) if login/session persistence is used at all during SKO. Better: avoid session save/load entirely for the SKO exercise — it's not needed for public-web account research and removes a whole failure class. |
| **No auth, no audit trail, no rate limiting today.** OAuth is coded but disabled by default (`src/auth.py:8-15`); the audit-logging/rate-limiting middleware described in `docs/fastmcp-enhancements-guide.md:38-136` is **proposed, not shipped**. A room of 30 reps hitting the connector simultaneously has zero per-user attribution if something breaks, and nothing stops one runaway loop from starving everyone else. | Confirm with whoever owns the Railway deployment whether OAuth has since been turned on. If not, treat this as a **shared, unauthenticated resource for the duration of SKO** — brief reps that this is a shared connector (not "your own browser"), set expectations about occasional slowness, and have Dave/facilitators monitoring Railway logs live during the competition segment. |
| **Bot-detection failures mid-demo.** Even with stealth.js + Bing default, the team's own research says Railway/GCP IPs are pre-flagged (`.claude/cache/agents/oracle/output-20260327-stealth-research.md:6`) and Google explicitly is NOT reliable. If a rep's prompt nudges the model toward `engine="google"` or toward `web_search` on a site that gates bots, the live demo could visibly fail with a CAPTCHA page. | Hard-code Bing (or the curated navigation-first source list from gap #1) as the *only* research path in the sales skill's instructions — don't let reps/models freely choose Google. Pre-test the actual hospitality-prospect companies that will be used in the competition exercise a day or two before SKO, not on the day. |
| **httpOnly cookies / real logins don't survive.** `web_save_session` (`src/tools/session.py:13-41`) captures `document.cookie` + localStorage/sessionStorage only — httpOnly session cookies (which most real login flows use) are invisible to JS and won't be captured. Any exercise assuming "log into LinkedIn once, stay logged in for the room" will not work reliably. | Don't build any part of the SKO exercise around a shared authenticated session; keep it to public-web content only (this reinforces the LinkedIn scope call in gap #3). |
| **Redeploys during the event wipe state.** Both the session store and (implicitly) any in-flight browser tabs are process-local; a Railway redeploy or crash-restart (`restartPolicyType: ON_FAILURE`, `railway.json:11-12`) during the competition would silently reset everything mid-exercise. | Freeze deployments (no pushes to the Railway service) for the duration of the SKO session; have a rollback plan and someone watching `/health` and Railway logs live. |
