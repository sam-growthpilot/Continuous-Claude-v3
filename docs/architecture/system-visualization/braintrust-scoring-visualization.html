01 · Foundations

The system that
scores itself.

Four TypeScript hooks emit a 0–1 score to Braintrust on the events they already fire on: a memory recall, a session-start health sweep, a Ralph task transition, a skill invocation. The scores are quality telemetry — "is the memory system actually relevant? are the hooks healthy? did the agent succeed? did the right skill trigger?" A single shell guard, INVARIANT_4, keeps all four emit sites alive against the one failure mode that kept silently deleting them: agent rewrites.

A hook scores itself
The observability pillar. Braintrust is the 6th pillar of CCv3 (alongside Memory, Hooks, Agents, PageIndex, Workflows). The Python side (braintrust_hooks.py) owns span/event creation; this TS helper owns score emission. Everything fails open — if Braintrust is unreachable or tracing is off, the hooks behave exactly as if scoring didn't exist.

02 · Foundations

Four dimensions, four hooks,
one emit helper.

Each dimension is a 0.0–1.0 float keyed by name in the scores object. A score near 1.0 is "good" (relevant, healthy, succeeded, correctly triggered); near 0.0 is "bad." The hook builds the payload from data it already has in hand, then awaits the emit. These four names are the exact strings the invariant guard expects to find.

memory_recall_relevance

memory-awareness.ts:595

Metadata: mode, daemon_ready, results_count, kept_after_floor

Fires on: every UserPromptSubmit recall

hook_health_ratio

hook-health-monitor.ts:322

ralph-task-monitor.ts:209

03 · Foundations

One fail-open helper,
shared by all four.

shared/braintrust-score.ts exports a single function: emitBraintrustScore(opts). Its design contract is non-negotiable — it never throws. Every skip condition returns silently. It resolves the project id, builds the feedback entry, and POSTs to Braintrust under a 2-second timeout. If anything goes wrong, the worst case is a breadcrumb on stderr.

emitBraintrustScore() decision flow

Why await — not void

The earlier code marked the call void emitBraintrustScore(...) — fire-and-forget. The problem: a hook process can process.exit() the moment its synchronous work is done. A floating promise mid-flight (the project lookup, the feedback POST) gets killed before the request lands. The score silently never arrives. Switching to await holds the process open until the POST resolves (or the 2s timeout fires). Same fail-open guarantee, but the request actually completes.

The process.exit race is exactly what INVARIANT_4 protects. The audit grep requires await emitBraintrustScore( on one line. A revert to void, or splitting the call across lines, makes the grep miss it — the count drops below 4 — and the guard FAILs.

Project-id resolution

  1. BRAINTRUST_CC_PROJECT_ID — direct, cheapest path, no lookup
  2. else BRAINTRUST_CC_PROJECT (default claude-code) → GET /v1/project?project_name=…
  3. Result cached in-process (one hook invocation = one Node process)
  4. Lookup failure / no objects / missing id → return null → skip

Skip conditions (all silent)

  • TRACE_TO_BRAINTRUST != "true"
  • BRAINTRUST_API_KEY missing / empty
  • spanId empty
  • scores object empty
  • project id unresolvable
  • fetch fails (network / timeout / non-2xx)

The feedback payload — what travels to Braintrust

// shared/braintrust-score.ts:211 — endpoint POST {API_URL}/v1/project_logs/{project_id}/feedback Authorization: Bearer {BRAINTRUST_API_KEY} // body shape (optional fields omitted when undefined) { "feedback": [{ "id": "<spanId>", "scores": { "<dimension>": 0.0–1.0 }, "metadata": { ... }, // only if provided "comment": "..." // only if provided }] }

The 2-second budget — BRAINTRUST_FEEDBACK_TIMEOUT_MS = 2000 — is enforced by AbortSignal.timeout() on both the project lookup and the feedback POST. It mirrors the dashboard-reporter pattern and is unit-tested to stay within 1000–5000 ms.

04 · The Guard

INVARIANT_4 — the count
that must never drop.

scripts/audit-braintrust-emits.sh does exactly one thing: it greps .claude/hooks/src/ for awaited emit call sites and FAILs if it finds fewer than four. It is not a linter and not a test runner. It is a tripwire for the one failure mode that kept silently dropping emits — a sub-agent rewriting a whole hook file from its context window.

edit → audit → pass / fail

The grep, verbatim

# scripts/audit-braintrust-emits.sh INVARIANT_4=4 matches=$(grep -rn "emitBraintrustScore(" .claude/hooks/src/ --include="*.ts" \ | grep -v "__tests__/" \ | grep -E "await emitBraintrustScore\(") count=$(echo "$matches" | grep -c "emitBraintrustScore(") if [ "$count" -lt "$INVARIANT_4" ]; then echo "FAIL: Regression detected"; exit 1 elif [ "$count" -gt "$INVARIANT_4" ]; then echo "WARN: update INVARIANT_4"; exit 0 else echo "OK: Emit count matches invariant (4)."; exit 0 fi

Three filters: (1) all emitBraintrustScore( calls, (2) drop __tests__/ (the test file has its own calls), (3) keep only lines with the await prefix. The third filter is the load-bearing one — the old grep matched both void and await and would have reported green on a pure await→void revert.

The two-line banner — DO NOT MODIFY

The script header carries an explicit instruction: "DO NOT MODIFY THE INVARIANT_4 LINE… If it FAILS, fix the code it points at — NEVER lower the invariant to silence it." This exists because the baseline was lowered exactly once (Gate 0.7+0.8) to silence a regression, and immediately restored. The rename from BASELINE to INVARIANT_4 is itself a defense — "invariant" signals "do not edit" where "baseline" sounded adjustable.

When you actually add a 5th dimension

Adding a legitimate new score dimension means a 5th awaited emit site. The audit then prints WARN: 5 emits found, invariant is 4 and exits 0 (not a failure). At that point you intentionally bump INVARIANT_4=5. The WARN path is the only sanctioned reason to touch that line.

Run it after any TS hook edit. The audit is invoked manually (and the orchestrator re-runs it after any spark touches hook code). It is also referenced by Spark Rule 7 — that agent-side rule is the real guard; the script header is for human readers reviewing the diff. bash scripts/audit-braintrust-emits.sh

The memory-awareness.ts emit block is a recurring victim. The pattern has a name: the agent-rewrite collision. The guard exists because the failure is invisible without it.

The 2026-05-23 hardening:
R1 + R2 + R3 + R5 + R6 + R9.

After regressions #6 and #7, six recommendations from the spark-agent-issues post-mortem shipped across four commits. They attack the failure from both ends: tighten the guard so a revert can't hide (R2), and constrain the agent so it doesn't rewrite whole files (R1, R3, R5, R6, R9).

Tighten the guard (R2)

Before: grep matched void OR await. A pure await→void revert kept the count at 4 — green, undetected. After: the grep requires await emitBraintrustScore( on one line. The revert that caused regression #6 now drops the count and FAILs. The variable name change (INVARIANT_4) is a behavioral nudge against the "lower the baseline" instinct.

Constrain the agent (R1/R3/R5/R6/R9)

The guard catches the regression; the spark constraints prevent it. R1 forbids whole-file rewrites. R3 says one spark per file for mechanical fans. R5 forbids touching the guard. R6 kills the phantom-linter misdiagnosis loop. R9 makes the orchestrator independently verify — because a spark can report "10/10 tests passed" (true) while silently dropping a sibling emit.

The cross-model telemetry parallel. Braintrust scores are to the memory/hook/agent/skill subsystems what codex-lift.jsonl is to cross-model review: a quantitative "is this earning its keep?" signal. Just as a consistently-zero codex_only count means the Codex pass isn't worth its quota, a consistently-low score dimension means that subsystem isn't delivering. Both are observability layers that score the thing they instrument.

07 · Operations

When a regression slips:
the exit ramp.

The orchestrator re-runs the audit after any spark touches hook code. If that re-run FAILs after the spark reported success, there is a 4-step recovery. The critical rule: do not re-spawn the same spark. Its context window has the regression baked in — the next attempt will reintroduce it.

regression detected → recovery flow
1

Diff — confirm it's a pure deletion

Run git diff HEAD -- <spark's edited files>. Confirm the regression is a pure deletion (the spark dropped sibling content) and not an intentional restructure. The signature: await emitBraintrustScore lines disappearing.

git diff HEAD -- .claude/hooks/src/*.ts
2

Restore — git checkout HEAD on the file

Run git checkout HEAD -- <file> to restore it to the last good state. Do this BEFORE attempting any new edit — otherwise the regression appears in the next spark's context window and propagates.

git checkout HEAD -- <file>
3

Escalate — kraken, not a re-spawned spark

Do NOT re-spawn the same spark for the same task. Its context window has the regression baked in; the next attempt will likely reintroduce it. Escalate to kraken — or do the fix directly in the orchestrator if it's a one-line patch.

4

File — append the incident

Record the failing edit diff, the spark's task ID, what regression slipped, and the recovery path taken — to docs/spark-agent-issues-2026-05-23.md (or a follow-up dated doc). This is the missing exit ramp; without it the orchestrator can loop on the same regression by re-prompting the same spark.

docs/spark-agent-issues-2026-05-23.md
Why the orchestrator re-runs the audit itself. Spark may run the audit before its last edit, then report Audit: PASS. A second run from the orchestrator after the spark exits catches late regressions. Never trust the spark's self-reported PASS alone — that's the gap R9 closes.

08 · Operations

Environment switches
and failure modes.

The whole emit path is gated by two environment variables and degrades gracefully on every error. Below: the switches that turn scoring on, and the failure modes the system is built to survive — including the ones that defeat the guard rather than the emit.

Environment variables

VariableRoleDefault / effect when unset
TRACE_TO_BRAINTRUSTMaster on-switch — must be the string "true"unset → emit returns silently (no-op)
BRAINTRUST_API_KEYBearer token for the feedback POSTunset / empty → emit returns silently
BRAINTRUST_CC_PROJECT_IDDirect project id — cheapest path, no lookupunset → fall back to name lookup
BRAINTRUST_CC_PROJECTProject name for /v1/project lookupunset → claude-code
BRAINTRUST_API_URLOverride the API host (staging / self-host)unset → https://api.braintrust.dev
BRAINTRUST_SESSION_IDSpan id for the hook-health emitunset → falls back to input.session_id

Two ways to be off: tracing disabled, or no key. Both are silent. This is why the hooks behave identically on a dev machine with no Braintrust account — the scoring layer simply doesn't run.

A real feedback payload, annotated

{ endpoint "POST /v1/project_logs/{id}/feedback", id "<braintrust span_id>", scores: { memory_recall_relevance 0.016, memory_recall_hit 1.0 }, metadata: { mode "hybrid", daemon_ready true, results_count 3, kept_after_floor 3 } }

A score of 0.016 is a healthy hybrid-RRF top score (the RRF sum maxes near 0.016 — see the memory deep-dive). Low absolute number, high relevance. memory_recall_hit: 1.0 confirms a result survived the floor.

Failure modes — emit path vs guard path

FailureLayerBehaviorDefense / recovery
Tracing off / no key emit ✓ silent skip Returns before any network call. By design. Set TRACE_TO_BRAINTRUST=true + key to enable.
Braintrust unreachable / 5xx / timeout emit ⚠ WARN, exit 0 Breadcrumb to stderr; the hook continues normally. Fail-open contract. Score is lost, the hook is unaffected. 2s AbortSignal caps the wait.
await reverted to void guard ✗ count drops Scores silently never land (process.exit race). Audit FAILs (await-only grep). Restore await; never lower INVARIANT_4.
Count tampering (lower the invariant) guard ✗ guard defeated A lowered INVARIANT_4 hides a real regression. DO-NOT-MODIFY banner + the "fix the code, never lower" rule. Caught in diff review.
File deletion (whole emit block dropped) guard ✗ silent loss The 6× recurring agent-rewrite collision. Audit FAILs; 4-step recovery (diff → checkout HEAD → kraken → file incident).
Self-introduced syntax error guard ✗ build breaks e.g. async function await emitX(. Build/tsc fails loudly; restore from HEAD, escalate (don't re-spawn).

Healthy signatures

The irony, stated plainly. This page documents the audit guard. Authoring it must not break the audit guard. The four emit sites stay at 4/4; the only files this deep-dive touches are HTML. The guard that protects the scoring layer is itself protected by the rule that you read hook source — you never edit it to write docs about it.
