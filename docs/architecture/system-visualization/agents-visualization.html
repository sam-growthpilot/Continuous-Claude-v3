01 · Foundations

39 specialized sub-agents,
one clean coordinating context.

The main session is a coordinator, not a worker. Reading 3+ files, running tests, external research, implementation — each spawns a sub-agent through the Task tool. The sub-agent runs in an isolated context window, burns its own tokens, and returns only a summary. The main thread stays lean, so it can orchestrate longer without drowning in detail.

When to delegate

  • Reading 3+ files → scout
  • External research → oracle
  • Implementation → kraken / spark
  • Running tests → arbiter / atlas
  • Debugging → debug-agent / sleuth
  • Mechanical N-file edit → N parallel sparks, one file each

The model rule

Every agent declares model: in its frontmatter. Two tiers only:

opus · deep judgment sonnet · throughput
Never haiku. Not even for quick tasks. Cheap models miss cross-file relationships and waste more time than they save. Omit model to inherit opus.

02 · Do the work

Writing code — size the agent to the change.

Three implementers, chosen by blast radius. kraken for complex work that earns a full TDD loop. spark for tiny mechanical edits. phoenix plans the refactor that kraken then executes. Two specialists round out the category: agentica-agent for building Python agents, onboard for orienting in a brownfield repo.

10 · Mechanics

The spawn lifecycle — .md to summary.

Every delegation runs the same path. The Task tool names an agent. Its definition comes from a .json sidecar — regenerated from the canonical .md frontmatter by sync-agent-json.py. The prompt loads into a fresh isolated context window. The agent works, emits a ralph_status JSON block, and the orchestrator verifies the claim before trusting it.

Full spawn lifecycle

The .json sidecar

Each <name>.md with a matching <name>.json gets its sidecar rebuilt so description / tools / prompt mirror the canonical markdown — while spawn-only fields are preserved.

{ "name": "kraken", "description": "... TDD workflow", "prompt": "# Kraken\n...", "tools": ["Read", "Edit", "Bash", ...], "model": "opus", // spawn-only "permissions": "skip", // spawn-only "blocked_patterns": [], // spawn-only "inherit_blocks": true }

Regenerate: python scripts/sync-agent-json.py --target .claude/agents --apply

ralph_status — the completion contract

Agents end with a machine-readable status block. In Ralph mode this is required — the orchestrator parses it to decide retry vs advance.

{ "ralph_status": { "task_id": "6.2", "status": "complete", "commit": "none" } }
Verify, don't trust. A "complete" claim is not proof. The orchestrator re-runs tests / the emit-invariant guard before accepting it — agents have regressed work and self-reported success.

Retry escalation chain

AttemptActionRationale
1Same agent, original instructionFirst honest pass
2Same agent + error contextSelf-healing with feedback
3Escalate to sparkQuick-fix specialist
4Escalate to debug-agentRoot-cause analysis
5BLOCKEDUser intervention required

Ralph iteration limits bound the loop: 10 (small) · 30 (medium) · 50 (large). Never loop silently — escalate after the limit with what was tried, what failed, and a recommended next step.

Why isolation matters. Each sub-agent's reads, searches, and dead-ends stay in its context, not the orchestrator's. That's the whole point — the main thread receives a digest, not a transcript, and can coordinate far longer before hitting its own limits.
