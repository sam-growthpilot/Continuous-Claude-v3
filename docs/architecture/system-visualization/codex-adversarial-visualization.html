01 · Concept

Same training family,
same blind spots.

The CCv3 review stack — critic, judge, principal-reviewer, liaison, surveyor — is entirely Claude-family. Same family means same blind spots. Codex (OpenAI, a different training family) reviews the same change in parallel. The findings only Codex catches are the cross-model lift — the tigers Claude can't see because of where it came from.

Reviewer model

gpt-5.5

@ xhigh reasoning · OpenAI Codex

Two modes

code / plan

git diff · markdown plan file

Sandbox

read-only

adversarial review never writes

Cross-model triangulation
The lift, not the overlap. Findings BOTH critic and codex-adversary flag are high-confidence — two independent families agree. Findings only codex-adversary flags are the cross-model lift: issues Claude structurally could not see. That lift is the entire justification for spending a Codex turn.

How Codex is wired in

  • codex-plugin-cc plugin — slash commands /codex:*
  • codex-adversary agent — used by /review and /premortem
  • plan-exit-premortem-prompt hook — offers /premortem after every approved plan
  • Requires @openai/codex CLI >= 0.131

When Codex review fires

  • /review — parallel Phase 1 alongside critic
  • /premortem — adversarial pass after inline imagining
  • After ExitPlanMode — AskUserQuestion offers premortem
  • Manual: /codex:adversarial-review --base <ref>

02 · Concept

The codex-adversary agent.

A thin orchestrator — not the reviewer itself. It assembles context, shells out to codex exec, captures the output, and returns a structured summary. The actual adversarial reasoning happens inside OpenAI's gpt-5.5 @ xhigh. The agent is the envelope; Codex is the letter.

Agent invocation flow

Mode: code

default

Reviews a git diff: git diff <BASE>...HEAD, or staged, or unstaged.

Diff capped at ~400KB to stay under Codex's prompt budget — if larger, most-changed files first.

Used by: /review Phase 1.

Mode: plan

mode=plan

Reviews a markdown plan file at an absolute path.

If the plan is >300KB, summarize the headings and feed the full body for the largest sections only.

Used by: /premortem Step 2.5.

The actual invocation

# .claude/agents/codex-adversary.md — Step 5 # Compose prompt to a temp file (avoids argv length limits on Windows) PROMPT_FILE="$(mktemp -t codex-adv-XXXXXX.txt)" # Model: env override, else gpt-5.5 (requires CLI >= 0.131; # fall back to gpt-5.4 on "requires a newer version" errors) CODEX_ADVERSARY_MODEL="${CODEX_ADVERSARY_MODEL:-gpt-5.5}" codex exec \ --model "$CODEX_ADVERSARY_MODEL" \ -c model_reasoning_effort=xhigh \ --sandbox read-only \ # review never writes files -C "$CLAUDE_PROJECT_DIR" \ - < "$PROMPT_FILE" \ # `-` = read prompt from stdin > "$OUTPUT_FILE" 2>&1 # capture stderr too (Codex streams progress)
Override the model with the CODEX_ADVERSARY_MODEL env var. The default is gpt-5.5; xhigh reasoning effort is fixed because adversarial review needs depth, not speed.

The adversarial framing — break confidence, don't validate

The agent locates the system prompt in priority order: repo-vendored copy at vendor/codex-plugin-cc/prompts/adversarial-review.md first (canonical, stable across machines), then plugin-cache copies, then an inline fallback. The framing tells Codex to default to skepticism.

#Attack surface (priority order)
1Auth, permissions, tenant isolation
2Data loss, corruption, or unrecoverable state
3Rollback / idempotency / re-entrancy hazards
4Race conditions and ordering bugs
5Observability gaps (silent failures, missing logs/metrics)
6Schema drift, migration hazards, backward incompatibility
7Cross-system contracts (API shape, event payload, retry semantics)

Finding bar: every finding cites file:line + a confidence 0.0–1.0 + a concrete recommendation. No style feedback. No praise. No summaries. If there's no real issue at the threshold, Codex says so.

What comes back

Raw Codex output is written to .claude/cache/agents/codex-adversary/latest-output.md — the canonical single-file convention (NOT output-{timestamp}.md), so synthesis consumers (review-agent, premortem) read a deterministic path. The agent returns a concise summary: verdict (needs-attention / approve), high/medium/low finding counts, and each finding prefixed [Codex].

03 · Integration

Inside /review — a fourth parallel reviewer.

codex-adversary runs in parallel Phase 1 alongside critic and two plan-reviewer passes. When all four return, review-agent synthesizes them — treating Codex as a distinct cross-model input source, never pooled with critic. Cross-model agreement is visible at a glance because Codex findings carry a [Codex] prefix.

/review — parallel reviews → synthesis

The synthesis convention

review-agent never merges Codex findings into the critic pile. They stay a separate column, prefixed [Codex], so a human reading the synthesis sees instantly which findings came from a different training family. Action items are grouped three ways:

GroupMeaningPriority
both-flaggedBoth critic AND codex-adversary flagged itHighest — two families agree
[Codex]-onlyOnly Codex flagged it — the cross-model liftHigh — Claude structurally missed it
claude-onlyOnly the Claude-family reviewers flagged itPer severity

A real synthesis (auth review)

# Phase 1 returned: critic → 2 issues (1 minor, 1 major) codex-adversary → verdict=needs-attention, 3 findings # review-agent synthesis, grouped by source: Verdict: REQUEST_CHANGES Cross-model agreement (high confidence): 1. Add input validation to login() [critic + [Codex]] [Codex]-only (cross-model lift): 2. session token rotation not idempotent under concurrent login 3. token format change has no migration path for in-flight sessions Non-blocking (claude-only): 4. standardize error messages [critic] Telemetry: critic_only=1, codex_only=2, both=1

Findings #2 and #3 are the payoff — a race condition and a missing migration path that the Claude-family reviewers didn't surface. codex_only=2 is logged to codex-lift.jsonl (Phase 3).

Modes within /review. /review --quick runs critic only (fast feedback, no Codex). /review --security adds the aegis security agent. /review --no-codex skips the Codex pass entirely — see the When to skip section.

04 · Integration

Inside /premortem — the tigers Claude missed.

Premortem asks: "Imagine it's 3 months from now and this failed spectacularly — why?" Claude first builds its own verified list of tigers, elephants, and paper tigers. Then, at Step 2.5, codex-adversary runs in mode=plan against the same plan file to find failure modes Claude's training family is blind to.

The risk vocabulary (Shreyas framework)

CategorySymbolMeaning
Tiger[TIGER]Clear threat that will hurt us if not addressed
Paper Tiger[PAPER]Looks threatening but probably fine
Elephant[ELEPHANT]Thing nobody wants to talk about

Step 2.5 — the cross-model pass

# Spawn codex-adversary in plan mode, pointed at the plan file Task( subagent_type="codex-adversary", prompt=""" ## Mode plan ## Scope [absolute path to plan file being pre-mortemed] ## Focus Identify failure modes Claude missed. Claude already found: [list claude_tigers with one-line descriptions] Look for additional tigers, elephants, or cases where Claude's paper_tigers were dismissed incorrectly. Different training family = different blind spots — that's the value. """ )

Merge convention: Codex findings get the [Codex] prefix and merge into the same tigers / elephants / paper_tigers lists, deduplicated by file:line + risk. Findings BOTH models flag are marked confidence: cross-model-agreed — act on those first. Findings only Codex flags are the cross-model lift.

This visualization is dogfood. The ccv3-visualization plan that produced this very page went through /premortem with the Codex pass. Codex surfaced failure modes Claude's premortem missed — including T-2, T-4, and E-3 (a tiger pair plus an elephant). Those would have shipped as latent defects without the cross-model pass.

Verify before flagging — both models obey this

Premortem's iron law: do NOT flag risks on pattern-matching alone. Every potential tiger goes through a verification checklist — read ±20 lines of context, check for an if exists() / try/except / else fallback, confirm it's in scope, confirm it's not dev-only code. If any check is "no" or "unknown", it is NOT a tiger. Every verified tiger must cite mitigation_checked — the specific mitigation that was looked for and not found.

Severity gate. HIGH tigers are blocking — must be addressed or explicitly accepted. MEDIUM informs the user. The plan file gets a ## Risk Mitigations (Pre-Mortem) section recording tigers addressed, accepted risks, and the run's claude-only / codex-only / both counts.

05 · Integration

The auto-prompt hook —
premortem offered, every plan.

plan-exit-premortem-prompt.ts fires on every ExitPlanMode. It's a pure context-injection hook — it never blocks and never writes state. It injects a directive telling Claude to call AskUserQuestion offering to run /premortem (with the Codex cross-model pass) on the just-approved plan. The hook only offers; it never auto-runs Codex.

ExitPlanMode → offer premortem

The injected directive

// plan-exit-premortem-prompt.ts — buildDirective() A plan was just approved (at `${planPath}`). Before proceeding to implementation, use the `AskUserQuestion` tool to ask the user: Question: "Run /premortem (with Codex cross-model adversarial pass) on this plan before implementation?" Header: "Premortem" Options: - "Yes -- run /premortem now (Recommended)" - "Skip -- proceed to implementation"

extractPlanPath() pulls a plan path from the tool input only if it looks like one — a single line, under 500 chars, containing a path separator or ending in .md. Otherwise the directive falls back to the generic "A plan was just approved." phrasing.

Fail-open by design

Any error — malformed input, non-ExitPlanMode tool, JSON parse failure — returns {}. The hook can never break the plan-approval flow. It coexists with plan-exit-tracker (which writes the plan-approved state file); both fire on the same tool event without interfering.

Offer ≠ run

The hook is the only auto-trigger in the Codex stack, and it just surfaces a question. No Codex turn is spent until the user picks "Yes" and /premortem actually invokes codex-adversary. The quota stays under human control.

06 · Operations

Is Codex earning its quota?
codex-lift.jsonl answers.

Every /review and /premortem run that includes Codex appends one row to .claude/logs/codex-lift.jsonl: how many findings were claude_only, how many codex_only, how many both. The codex_only count is the cross-model lift. If it's consistently zero, Codex is duplicating Claude's work and the quota cost isn't justified.

The schema, annotated

{ ts "2026-05-21T18:42:00Z", // ISO 8601 UTC skill "review" | "premortem", // which skill wrote the row scope "PR-#123" | "plans/foo.md", // what was reviewed claude_only 3, // only Claude/critic flagged codex_only 2, // THE LIFT both 4, // both flagged (high-confidence) via "direct" | "envoy" // transport }

For /review, "Claude" means the combined critic + plan-reviewer outputs. For /premortem, "Claude" means the inline 3-category risk framework output.

The adoption decision threshold

If after 20+ runs avg(codex_only) < 0.2, the README says to consider: (1) tightening the adversarial-review prompt at vendor/codex-plugin-cc/prompts/adversarial-review.md, (2) disabling the default Codex pass and making it opt-in (a --codex flag instead of --no-codex), or (3) investigating whether Codex output is being filtered out incorrectly during synthesis.

Committed, not gitignored. codex-lift.jsonl is a small, valuable signal over time — it stays in git so the lift trend survives across machines and sessions.

07 · Operations

Cost model: your ChatGPT subscription,
not an API key.

Codex authenticates via OAuth against the ChatGPT subscription (Plus/Pro), not an OpenAI API key. There is no separate API billing — every adversarial-review call counts against that subscription's quota. If codex login status shows a logged-in ChatGPT account, the integration is live.

What one invocation costs

  • Spends one Codex turn at gpt-5.5 (default) — or whatever CODEX_ADVERSARY_MODEL resolves to — at xhigh reasoning effort
  • xhigh is the expensive setting; it was chosen because adversarial review needs depth, not speed
  • A typical /review with Codex = 1 Codex call. A typical /premortem with Codex = 1 Codex call
  • The auto-prompt hook only offers premortem — it never auto-runs, so it costs zero quota on its own

Safe commands (no confirmation)

  • codex login status — check auth without re-prompting
  • codex --version, codex --help
  • codex exec --sandbox read-only
  • /codex:review, /codex:adversarial-review
  • /codex:status, /codex:result, /codex:cancel

Confirm-first commands (always ask)

  • /codex:rescue — delegates execution, can modify files
  • codex exec --sandbox workspace-write / danger-full-access
  • codex exec --dangerously-bypass-approvals-and-sandbox
  • /codex:setup --enable-review-gate — DO NOT enable (high-cost, 900s timeouts, high-risk on Windows)

The default vs the gate

The default Codex involvement (parallel in /review, a pass in /premortem) is deliberately bounded to one turn per workflow. The thing to avoid is /codex:setup --enable-review-gate, which wires Codex into every turn at a 900-second timeout — documented as quota-draining and high-risk on Windows. The adversarial agent stays a per-workflow tool, not an always-on gate.

08 · Operations

When to skip Codex — --no-codex.

Codex review costs a real turn against the ChatGPT subscription and adds 30–120 seconds of latency. For changes where the cross-model lift can't pay for itself, pass --no-codex to /review or /premortem. The decision is about whether a different training family would plausibly catch anything the Claude-family reviewers missed.

The decision table

SituationCodex?Why
Doc-only changes (.md, .json comments) skip No logic for a different family to attack — waste of quota
Hotfix where latency matters skip 30–120 s pass isn't worth it when you need to ship now
Trivial diff (<20 lines, single file, no logic change) skip Cross-model lift is near-zero on tiny changes
ChatGPT subscription quota exhausted this session skip No turns left to spend — Claude-only review still runs
Auth, data-loss, migration, or concurrency changes keep Highest-value attack surface — exactly where cross-model lift pays off
Architectural plan before implementation keep Premortem is cheap leverage — catch failure modes before code exists
PR touching shared contracts or public API keep Cross-system contract bugs are a top Codex attack-surface category
Skip-or-keep decision flow

The synthesis lift, restated

When you keep the Codex pass, review-agent treats its output as a distinct cross-model input source — never pooled with critic. The [Codex] prefix makes cross-model agreement visible at a glance. Findings BOTH families flag are high-confidence. Findings only Codex flags are the lift — and the codex_only column in codex-lift.jsonl is how you prove, over time, that the pass is worth the quota.

Rule of thumb. Skip Codex when the diff has no logic a different model could meaningfully attack (docs, trivial, hotfix) or when there's no quota to spend. Keep it whenever the change touches auth, data integrity, migrations, concurrency, or cross-system contracts — the categories where a second training family pays for itself.
