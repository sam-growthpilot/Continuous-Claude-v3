## 2. Frontier scan

Every arXiv ID and URL below was fetched and confirmed this session; I quote only what each source's abstract/text actually states. Anything from a secondary summary is tagged **[summary-only]**. (A background `oracle` research pass surfaced additional candidates — SlopCodeBench 2603.24755, SWE-Chain 2605.14415, RoadmapBench 2605.15846, AgentForge 2604.13120, AgentLTL 2607.02599, BT-sigma jury 2602.16610 — that I did NOT independently full-text verify this session; they are excluded from the numbered citations below rather than cited on snippet evidence.)

1. **Anthropic — Building effective agents** (https://www.anthropic.com/engineering/building-effective-agents, verified live). Still the reference vocabulary: *workflows* = "LLMs and tools orchestrated through predefined code paths"; *agents* = systems where "LLMs dynamically direct their own processes and tool usage." Named patterns: prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer. Core guidance: "find the simplest solution possible, and only increasing complexity when needed… only when it demonstrably improves outcomes."

2. **Sherlock: Reliable and Efficient Agentic Workflow Execution** (arXiv 2511.00330, verified). *New since the last pass.* Tackles error propagation across workflow steps where "incorrect or partially correct output at one step can propagate or even amplify through subsequent stages," and that verifying *every* step "introduces significant latency and cost overhead." Mechanism: counterfactual analysis to find error-prone nodes, **selectively attach cost-optimal verifiers**, and speculative execution (downstream runs speculatively while verification happens in the background; "execution is rolled back to the last verified output" on failure). Reported: **18.3% average accuracy gain** vs a non-verifying baseline, **up to 48.7% execution-time reduction** vs non-speculative verification, **26.0% lower verification cost** vs Monte-Carlo-search methods.

3. **Difficulty-Aware Agentic Orchestration for Query-Specific Multi-Agent Workflows** (arXiv 2509.11079, verified). *New since the last pass.* Proposes DAAO — dynamically adjusting multi-agent workflow complexity to predicted query difficulty, "enabling simpler workflows for easy queries and more complex strategies for harder ones," using a difficulty estimator + a self-adjusting policy. The frontier is moving from static workflow selection toward difficulty-predicted allocation.

4. **Can LLM-as-a-Judge Reliably Verify Rubrics in Agentic Scenarios?** (arXiv 2606.29920, verified). On judging rubric satisfaction over agent trajectories (RuVerBench, 2,458 human-annotated instances): "even the most advanced models achieve strong performance but still exhibit substantial noise," and "majority voting yields effective but diminishing returns." (Correction to the 2026-07-03 pass, which characterized this as "sub-human/sub-SME agreement" — the abstract states *noise* and *diminishing returns from voting*, not an explicit sub-SME gap.)

5. **Reliability without Validity: A Systematic, Large-Scale Evaluation of LLM-as-a-Judge Models Across Agreement, Consistency, and Bias** (arXiv 2606.19544, verified). *New this pass.* The sharpest judge-reliability finding of the period: "high test–retest reliability (>0.95) coexists with severe position bias (>0.10) in two production-deployed judges" — a **consistency-bias paradox**. A judge can look rock-solid across repeat runs while being systematically biased. Direct justification for not trusting a single stable-looking judge at a hard gate.

6. **Evaluating Plan Compliance in Autonomous Programming Agents** (arXiv 2604.12147, verified). Treats plan compliance as distinct from task success: without it "it is impossible to assess whether a solution was reached through correct strategic reasoning or through other means." Analyzed ~17,000 agent trajectories and found "agents often fall back on internalized training patterns rather than following explicit guidance" — i.e., agents pass while drifting off the approved plan.

7. **SWE-EVO: Benchmarking Coding Agents in Long-Horizon Software Evolution Scenarios** (arXiv 2512.18470, verified). *New concrete numbers this pass.* 48 tasks "requiring multi-step modifications spanning an average of 21 files, validated against test suites averaging 874 tests per instance." Headline: "GPT-5.4 with OpenHands achieves only 25% on SWE-EVO versus 72.80% achieved by GPT-5.2 on SWE-Bench Verified" — a ~48-point drop moving from single-issue patches to multi-file evolution. Strong quantitative support that bounded-iteration + fresh-context re-prompting is a design necessity, not a stylistic choice.

8. **Anthropic — "Dynamic Workflows" in Claude Code** (https://www.infoq.com/news/2026/06/dynamic-workflows-claude-code/, verified live; June 2026). *New this pass — vendor-level convergent validation.* Claude Code now "dynamically create[s] orchestration scripts, break[s] work into subtasks, run[s] them in parallel, and validate[s] results before presenting a final answer," and "plans the work, distributes tasks across specialized agents, compares and verifies findings, and iterates until results converge." This is structurally the same fan-out → verify → iterate-until-converge pattern the CCv3 harness already exposes as the Workflow tool — i.e., the tool CCv3 owns but has never saved a script for is now Anthropic's own headline direction. (I do not attribute the specific "JavaScript" / "Performance Outcomes grader" internals to this article — the fetch did not confirm those.)

9. **DBOS — durable execution as an in-process Postgres library** (https://www.dbos.dev/blog/durable-execution-crashproof-ai-agents, verified live). Durable execution stores workflow/step state in Postgres from an in-process library (`@DBOS.workflow()`/`@DBOS.step()`), so "if a server crashes mid-workflow, the system resumes exactly where it stopped — no duplicate refunds processed — because each step's completion is recorded in Postgres before moving to the next step."

10. **Diagrid — Checkpoints are not durable execution** (https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows, cited 2026-07-03; consistent across this session's search). Graph-checkpoint frameworks (LangGraph, CrewAI, ADK) save state *between* nodes but not *inside* a node — "intermediate work within a single node is lost if a failure occurs" **[summary-only, this session]** — so the first replayed step can double-apply side effects. True durable execution (Temporal/DBOS) makes each step individually retriable without double-applying.

11. **The Orchestration of Multi-Agent Systems: Architectures, Protocols, and Enterprise Adoption** (arXiv 2601.13671, verified). A "unified architectural framework integrating planning, policy enforcement, state management, and quality operations," with MCP and Agent2Agent as the "interoperable communication substrate that enables scalable, auditable, and policy-compliant reasoning." (I do not attribute a specific topology taxonomy to this paper — the abstract does not enumerate one.)

12. **LangGraph + Temporal production consensus, 2026** **[summary-only]** (WebSearch synthesis of multiple 2026 posts, e.g. diagrid above and vendor blogs). The shipping pattern is layered: LangGraph as the reasoning/decision layer, a durable-execution engine (Temporal/DBOS) as the infrastructure-durability layer — "more boring and more reliable than either alone." I could not confirm the specific LangGraph durability-mode names (`exit`/`async`/`sync`) against the primary LangChain doc this session, so I do not cite those specifics.

## 4. Recommendations

The 2026-07-03 recommendations R1–R5 remain valid and unshipped; I re-state them with fresh evidence and two refinements. R6 is re-scoped given the correction above, plus one new item (R-NEW).

**R1 — Add a plan-compliance check to Ralph's merge gate. ADOPT.** (Carried; strengthened.)
Src 6 (2604.12147, ~17k trajectories) is direct new evidence that agents pass while drifting off the approved plan — exactly what the premortem-approved task list was meant to prevent. Extend the 4.1.5 `plan-reviewer` prompt to also grade the diff against `/tasks/tasks-<feature>.md`: flag files touched outside the declared list and tasks marked complete with no corresponding diff. Effort **S** (prompt/checklist extension + one section in `references/patterns.md`). Risk near zero (adds a report; blocks nothing new on its own).

**R2 — Add ONE cross-model second opinion at the merge gate — not a full panel. ADOPT (refined down).**
2026-07-03 R2 proposed a 3-way all-must-pass panel. New evidence argues for *less*: src 5's consistency-bias paradox (a judge can be >0.95 self-consistent yet severely biased) says our lone `plan-reviewer` looking stable across runs is *not* evidence it's right; src 4 says voting has diminishing returns; src 2 (Sherlock) says verify **selectively at the error-prone node** with cost-optimal verifiers. So: keep the merge gate as (a) the test suite (tool-grounded truth) + (b) `plan-reviewer` with the R1 plan-compliance check + (c) **one** cross-model reviewer (`codex-adversary`, already exists) over `git diff main...HEAD`. That's a 2-opinion gate on the one irreversible node, not a heavyweight jury everywhere. Degrade to (a)+(b) with a logged warning if the cross-model call errors (don't let a flaky Codex call deadlock a merge). Effort **S–M** (skill edit + one spawn per Ralph run, gated to the merge only). Cost: ~1 Codex call/feature, consistent with existing /review posture.

**R3 — Audit journal/checkpoint resume for first-replayed-step idempotency. ADOPT (audit-first).** (Carried unchanged.)
Src 9–10 restate the sharpest line: checkpoint-level resume (`.ralph/state.json` + `reconcile`; the Workflow-tool journal) does not make the step in flight at crash time safe to replay. Concrete CCv3 scenario: agent crashes after `git commit` but before `ralph_status` is recorded → resume re-runs the task → duplicate/conflicting commit. Audit `ralph-state-v2.py` + `ralph-progress-sync.py` resume paths; where a double-apply window exists, make the replayed step idempotent (check for the task's `ralph_status.commit` hash in `git log` before re-spawning). Effort **S** audit, **S–M** fix. Adopting a durable-execution engine (Temporal/DBOS): **SKIP for now** — but if the audit finds real windows, a DBOS-style Postgres step ledger is the lowest-infra fix since Postgres already runs (src 9). [Speculation: the window exists — the audit confirms or clears it.]

**R4 — Codify /review as the first saved native Workflow-tool script. ADOPT (start small).** (Carried; now with vendor validation + a verified headless data point.)
CCv3's stated bet (deterministic over model-driven) matches src 1/11, and src 8 shows Anthropic itself now ships exactly this fan-out→verify→iterate pattern into Claude Code — yet CCv3's copy of the engine ships unused. Encode /review Phase 1 (critic ∥ codex-adversary ∥ plan-reviewer → synthesis, schema-forced findings arrays) as a saved Workflow script. The schema option mechanically delivers the agents-proposal R2 structured-return contract for that path. Because the Workflow tool is available headless (verified this session), the same script can back scheduled report/review jobs. Keep the human synthesis/judgment step in the skill, not the script. Effort **M**. Risk: behavior fork between skill prose and script — mitigate by having the skill *invoke* the script (single source of truth). **Open:** `.claude/workflows/` is not in `SYNC_DIRS` (`.claude/rules/sync-known-gaps.md`) — decide the sync home before shipping.

**R5 — Port Ralph's phase-3 delegation loop into a Workflow script. WATCH.** (Carried unchanged.)
Biggest reliability win on paper (mechanized `task-start`/`complete`/`sync` vs prose), but the loop is deeply coupled to Python state tooling + AskUserQuestion checkpoints + HITL/AFK modes; the Workflow tool is headless. Re-evaluate after R4 proves the pattern and after the now-live enforcer hooks (R6) yield spawn-side telemetry so the loop's real failure rate is measurable. [Speculation: measure before porting.]

**R6 — Truth-up the docs and VERIFY the now-live workflow enforcers actually gate. ADOPT (re-scoped by this session's correction).**
The matcher flip already landed in active settings (verified: `maestro-enforcer` and `ralph-task-monitor` under `"matcher": "Task"`), so R6 is no longer "flip the matcher." It is now: (1) **truth-up** `CURRENT-STATE.md:39` and `BACKLOG.md:37,49` (they still say dead / QW-04-pending) and the overclaiming `maestro/SKILL.md:36-39`, `ralph/SKILL.md:33`, and RULES.md Maestro C:10 text; (2) **confirm the flip reached all three settings surfaces** (I verified active only; repo `settings.json` didn't surface these two); (3) **verify the now-firing hooks actually gate rather than merely log** — `ralph-delegation-enforcer` is soft since 2026-04-23 pending the ST-02 two-level `session_id + agent_id` identity fix, so a firing hook on a shared session_id may still not correctly distinguish orchestrator from subagent. Effort **S** (doc edits + a one-shot behavioral probe: spawn under Maestro's interview phase and confirm a non-scout agent is actually blocked). This is standing correctness/safety debt either way: today the docs *under*-claim (say dead when live) while the SKILLs *over*-claim (say hard-block when possibly log-only) — both mislead.

**R-NEW — Selective/speculative verification framing for the whole harness. WATCH.**
Sherlock (src 2) is the freshest idea of the period and generalizes: instead of "verify every step" (expensive) or "verify only at the end" (late), identify the *error-prone nodes* and attach cost-optimal verifiers there, running downstream speculatively. CCv3 already does a coarse version (per-task 3.5 checks + the 4.1.5 gate). Track whether a lighter, node-targeted verification policy (e.g., heavier verification only on tasks that touch >N files or the declared risk-list from premortem) beats uniform per-task verification. Ties naturally to DAAO (src 3): tier verification effort by *predicted difficulty*, not just task size. **WATCH** — adopt only if session scoring shows verification cost or missed-regression rate is a real problem; don't add a difficulty predictor speculatively.

**R7 — Difficulty-aware (vs size-based) iteration tiering. SKIP for now.**
DAAO (src 3) predicts difficulty to allocate workflow complexity. Ralph's 10/30/50 size tiers are a working heuristic at single-operator scale; a learned difficulty estimator is real frontier motion but over-built for one developer's harness. Revisit only if size-tiering visibly mis-allocates (small tasks blowing the iteration cap, or large tasks finishing trivially).
