# Hooks — Next-Evolution Proposal (2026-07-01)

## 1. Where CCv3 is today

CCv3's "hooks" ARE Anthropic's native Claude Code hook mechanism, used at scale: **112 TypeScript sources** in `.claude/hooks/src/` (Glob), esbuild-compiled to `dist/*.mjs`, registered in `settings.json` under event arrays with tool matchers. Verified facts:

- **Each hook is a standalone `type: "command"` Node process.** It reads the event JSON on stdin and writes a decision JSON to stdout (`.claude/hooks/src/guardrail-enforcer.ts:148-207`, `hook-health-monitor.ts:264-348`). There is no shared runtime, no in-process dispatcher, and no typed hook framework — every hook re-implements stdin parse, fail-open, and session-id derivation itself.
- **The decision contract is the native one.** PreToolUse hooks block via `permissionDecision: deny/allow/ask`; SessionStart/UserPromptSubmit/PostToolUse hooks inject `hookSpecificOutput.additionalContext` (`hook-catalog.md:106-118`, `hook-health-monitor.ts:334-340`).
- **CCv3 uses ~6 of the platform's events** (SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PreCompact, SessionEnd — `hook-catalog.md`). It uses **only the `command` handler type**, no `if`-conditions, and does not use `updatedInput` to rewrite tool args.
- **The strongest guards are genuinely deterministic and good.** `package-install-guard` runs a 4-layer supply-chain check (typosquat → local blocklist → OSV.dev → package-age) before any install (`hook-catalog.md:53`, `rules/package-install-safety.md`); `destructive-command-guard` gates recursive-rm/reset-hard/force-push after quote-stripping (`rules/destructive-commands.md`); `file-claims` (PreToolUse:Edit|Write) does cross-session file locking (`hook-catalog.md:55`). These are the parts to keep.
- **Observability exists but is thin.** 4 deterministic `emitBraintrustScore()` emitters (`memory-awareness`, `telemetry-tracker`, `ralph-task-monitor`, `hook-health-monitor`) plus `braintrust_hooks.py` session tracing; `hook-error-pipeline.ts` offers `wrapWithErrorCapture` (`.claude/hooks/src/hook-error-pipeline.ts:163-178`) but adoption is opt-in, not universal.

**Known limitations (Fable-5 review, verified in the repo):**
- **Matcher split-brain kills 12 safety/verification hooks.** They register under matcher `'Agent'` while the live tool emits `'Task'` — zero pre-spawn guard / post-spawn verification fires (`CURRENT-STATE.md:11,36`). The fix (`QW-04`, "flip `'Agent'`→`'Task'`") is **still unshipped** — it is the one remaining Wave-1 item (`BACKLOG.md:37,49`).
- **The context-bus symbol writer needs a `SubagentStop` hook that has zero registrations** (`CURRENT-STATE.md:12`, `ST-01`).
- **UserPromptSubmit serializes ~13 spawns → 22–32s worst case** (`CURRENT-STATE.md:36`, D6a-01, `ST-03` wants serial→parallel).
- **7 competing `getSessionId` implementations → 60.7% corr-null telemetry** (`CURRENT-STATE.md:13`, `ST-02`).
- **Enforcement is often soft / prompt-level, not tool-level.** `guardrail-enforcer` matches **regex keywords in the user's prompt text** with bypassable `antiTriggers` (`guardrail-enforcer.ts:31-80,152-168`), and its "block" is really context injection — the code itself notes "UserPromptSubmit hooks can't truly block - they inject context" (`guardrail-enforcer.ts:172`). Recently-fixed field-name bugs (`epistemic-reminder` read `input.tool` not `input.tool_name`, QW-05) show how fragile the hand-rolled parsing is.

## 2. Frontier scan (last ~6–12 months)

**The native platform itself has moved — and CCv3 has not kept up.** The current Claude Code hooks reference (https://code.claude.com/docs/en/hooks, fetched 2026-07-01) documents **30+ events** including dedicated `SubagentStart` / `SubagentStop` / `TaskCreated` / `TaskCompleted`, `PostToolUseFailure`, `PermissionRequest` / `PermissionDenied`, `PostToolBatch`, and `FileChanged`. Critically: **"All matching hooks run in parallel, and identical handlers are deduplicated automatically."** It also adds `permissionDecision: defer`, arg-rewriting via `hookSpecificOutput.updatedInput`, declarative per-hook `if` conditions (e.g. `"if": "Bash(rm *)"`), and four new handler types beyond `command` — `http`, `mcp_tool`, `prompt` (LLM yes/no), and `agent` (subagent verifies a condition). It explicitly flags the **deprecated `approve`/`block` fields** mapping to `allow`/`deny`.

**Agent-harness middleware converged on before/modify/after + block/rewrite.**
- **LangChain 1.0 (GA Oct 2025)** replaced ad-hoc `pre_model_hook`/`post_model_hook` params with composable middleware objects — `before_model`, `modify_model_request`/`wrap_model_call`, `after_model`, `wrap_tool_call` — with **onion ordering** (before-hooks first-to-last, after-hooks reverse) (https://docs.langchain.com/oss/python/langchain/middleware/custom, https://blog.langchain.com/agent-middleware/).
- **OpenAI Agents SDK** cleanly **separates enforcement from observation**: guardrails (input/output/**tool** guardrails that block *before and after* each tool invocation via a "tripwire") vs `RunHooks`/`AgentHooks` lifecycle observers (`on_tool_start`/`on_tool_end`), and traces guardrail decisions as first-class events (https://openai.github.io/openai-agents-python/guardrails/).

**Guardrail frameworks = intercept the tool-call boundary, richer than allow/deny.**
- **NVIDIA NeMo Guardrails** structures five rail stages — input / retrieval / dialog / **execution** / output (https://github.com/NVIDIA-NeMo/Guardrails). "Execution rails" gate tool/action invocation specifically (≈ PreToolUse), separate from output rails.
- **Invariant Guardrails** is the closest external analog to CCv3's hook layer: a rule-based **proxy** between the app and its MCP servers/LLM that intercepts *every* tool call, supports **dataflow rules** ("data from X must not reach sink Y"), and scopes rules hierarchically client→server→tool (https://github.com/invariantlabs-ai/invariant). Guardrails AI adds a per-check `on_fail` taxonomy richer than deny (reask / fix / filter / refrain / exception) (per oracle: https://guardrailsai.com/docs/concepts/validators).

**Deterministic policy-as-code at the tool boundary is now production.**
- **AWS Cedar in Amazon Bedrock AgentCore Policy** (verified 2026-07-01, https://aws.amazon.com/blogs/security/why-policy-in-amazon-bedrock-agentcore-chose-cedar-for-securing-agentic-workflows/): a Cedar engine attaches to a gateway that intercepts agent↔tool traffic, **blocks everything by default**, and policies selectively open specific tool invocations under conditions. The blog's argument is directly relevant: "the LLM can't affect the external world directly: it has to go through an orchestrator that invokes tools… This is precisely where the controls must be applied." Cedar policies are human-readable *and* **encodable as mathematical formulas** for automated conflict/logical-error detection — a property "a pile of imperative TS hooks" cannot offer.
- **OPA/Rego for agents**: `Input(JSON)+Policy(Rego)+Data(JSON)→Decision`, one Policy Decision Point in front of every tool call (https://codilime.com/blog/why-use-open-policy-agent-for-your-ai-agents/, https://tianpan.co/blog/2026-04-25-policy-as-code-agent-permissions-opa-rego).

**Security: the field converged on session-scoped dataflow, not per-call filtering.**
- **The lethal trifecta** (Simon Willison, 2025-06-16): danger = private-data access + untrusted-content exposure + external communication *in one session*; any two is safe (https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/). Per-call allow/deny cannot catch it — you need session state.
- **Meta's Agents Rule of Two** (2025-10-31): an agent should hold at most two of {untrusted input, sensitive access, external state-change} per operation; all three → mandatory human-in-the-loop (https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/). Willison's writeup reports a multi-lab paper that broke 12 published injection defenses under adaptive attack and named Rule-of-Two capability restriction the best *practical* advice.
- **CaMeL — "Defeating Prompt Injections by Design"** (arXiv 2503.18813, verified via abstract 2026-07-01): a capability/information-flow layer where a custom interpreter tracks provenance and **enforces security policies before each tool call**; solves **77% of AgentDojo tasks with provable security vs 84% undefended** — i.e. deterministic capability enforcement costs ~7 points of utility for a verifiable guarantee.
- **MCP tool poisoning / rug-pulls** (Invariant Labs, 2025-04): hidden instructions in tool *descriptions* (metadata the model trusts) execute with host privileges; a "rug-pull" server pushes poisoned descriptions on update and the host reloads without re-prompting (https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks). Named CVEs give it teeth (CVE-2025-54136 "MCPoison" rug-pull, per oracle secondary source).
- Benchmark motivation: on AgentDojo, tool-filtering reportedly cut attack-success from ~30% to ~7.5% at a utility cost (oracle secondary source https://www.emergentmind.com/topics/agentdojo-benchmark; treat the exact figures as secondary — CaMeL's 77/84 is the verified anchor).

## 4. Recommendations

**R1 — Re-target the dead agent safety/verification chain to the native `SubagentStart`/`SubagentStop` (+ `TaskCreated`/`TaskCompleted`) events instead of the `'Agent'`→`'Task'` matcher flip. ADOPT.**
QW-04's planned fix (flip the PostToolUse matcher to `'Task'`) revives the 12 hooks but keeps them coupled to a tool-name string that already drifted once. The platform now exposes **dedicated subagent lifecycle events** (https://code.claude.com/docs/en/hooks) that are the semantically-correct home for pre-spawn guards and post-spawn verification — no tool-name coupling to drift again. This directly upgrades `QW-04`, and gives `ST-01` its `SubagentStop` writer and `ST-10` its recall-injector seam natively. Rationale: fixes the single highest-leverage dead-hook problem *and* future-proofs it.

**R2 — Audit whether the native parallel-hook execution obviates ST-03, and adopt `updatedInput` + `permissionDecision: defer` + `if`-conditions. ADOPT (audit-first).**
The platform states matching hooks already run in parallel with dedup. The 22–32s UPS wall (`CURRENT-STATE.md:36`) is therefore either (a) intra-hook serial subprocess spawning inside one aggregator hook — a code fix regardless — or (b) a deployed-version gap. [Speculation until measured.] Either way, `ST-03`'s hand-rolled "serial→parallel" may be partly free; verify before building it. Separately, `updatedInput` lets guards *sanitize* a tool call instead of only denying it, and `if`-conditions move cheap pre-filters out of Node startup — both reduce cost and false-positives.

**R3 — Make "guard vs observer" a typed contract in a shared hook harness. ADOPT (small).**
Adopt the OpenAI-SDK/LangChain split: *guards* may deny/rewrite and run deterministically; *observers* (SubagentStop bus-writer, Braintrust emitters, telemetry) are side-effect-free and can never block. A thin shared harness (extending `hook-error-pipeline.ts`) that enforces this + centralizes stdin-parse, fail-open, and the canonical `getSessionId` (ST-02) removes the per-hook re-implementation that produced the QW-05 field-name bug and the 7-impl id split-brain.

**R4 — Add a session-scoped lethal-trifecta / Rule-of-Two capability guard. ADOPT (net-new capability).**
This is the frontier's *only* endorsed defense against adaptive prompt injection and CCv3 has nothing like it. A PreToolUse guard tracks per-session capability flags (touched-untrusted-content, touched-private-data) and gates the third capability (external send/exfil) — Meta's Rule of Two as a hook (https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/), the deployable shadow of CaMeL's IFC (arXiv 2503.18813). Highest *new* security value on this list.

**R5 — MCP tool-description integrity hook (hash + rug-pull detection). ADOPT (small).**
At SessionStart / on MCP (re)load, hash each tool description and alert on change; scan descriptions for injection patterns at registration (Invariant, https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks). This is the *exact same defense shape* as `package-install-guard` applied to the MCP supply chain — CCv3 loads dozens of MCP servers, so the surface is real.

**R6 — Extract *authorization* into a declarative, analyzable policy layer (Cedar/Rego-style). WATCH.**
The `rules/*.md` safety tables (neonctl/kusto/sentry/railway/destructive) are already half a policy set — but they are prose the model is asked to follow, not an enforced decision point. Cedar's provable-conflict-detection (https://aws.amazon.com/blogs/security/why-policy-in-amazon-bedrock-agentcore-chose-cedar-for-securing-agentic-workflows/) is the right end-state for authorization hooks. WATCH, not ADOPT: it is a large change, should gate on `ST-06` (permission-layer redesign) and `ST-02`, and needs a spike on whether a standalone Cedar/Rego eval fits a Windows TS hook cheaply.

**R7 — LangChain-style deterministic onion ordering for enforcement chains. WATCH.**
Native parallel+dedup changes the ordering story; a strict before-first/after-reverse order matters mainly if guards depend on each other's mutations. Low ROI for a single-operator system until R3's harness exists. WATCH.

**R8 — LLM-judgment guardrails (Llama Guard / native `prompt` & `agent` handler types). SKIP (this iteration).**
The native `prompt`/`agent` handlers and classifier guards (Llama Guard) add latency and token cost. CCv3's deterministic guards + R4/R5 cover the current threat model; revisit only if a check genuinely can't be expressed deterministically.

**R9 — Full guardrail-DSL rewrite (NeMo Colang / Invariant proxy). SKIP.**
Re-platforming 112 hooks onto a rail DSL or an external proxy is over-engineering for a single-operator harness. The lighter path is native events (R1/R2) + a typed harness (R3) + a policy layer for authorization only (R6). Absence here is a correct scoping choice, not a gap.

## 5. Integration approach

- **R1 (subagent events).** Files: `settings.json` ×3 (repo+active+template), the 12 agent-chain hooks (`agent-verification.ts`, `agent-model-guard`, `task-router.ts`, `pre-tool-knowledge.ts`, `tldr-context-inject`, `agent-recall-injector.ts`, `ralph-task-monitor.ts`, etc.), `bus-session-populator`/`SubagentStop` writer for `ST-01`. Ties: supersedes/upgrades **QW-04**; unblocks **ST-01** and **ST-10**. Effort ~M. Risk: the dedicated events' payload shape must be confirmed against the deployed CC build before re-registering (verify with one probe hook first — do not flip all 12 blind). What could go wrong: repeating the Agent/Task drift if the new event names aren't the deployed ones — mitigate by a single-hook canary + `hook-health-monitor` before/after.
- **R2 (platform primitives).** Files: whichever UPS aggregator holds the 13 spawns; `settings.json` `if`-conditions on `package-install-guard`/`destructive-command-guard`; guards that currently deny could gain `updatedInput`. Ties: **ST-03** (may shrink it), **SG-02** (drift reconciliation across the 3 settings surfaces). Effort ~S–M. Risk: `if`/`updatedInput`/`defer` support is deployed-version-dependent — gate on a capability probe.
- **R3 (typed harness).** Files: extend `hook-error-pipeline.ts` into a `createGuard`/`createObserver` pair; fold in the canonical `shared/session-id.ts` (ST-02). Ties: **ST-02**, and the emit-invariant guard (`scripts/audit-braintrust-emits.sh`). Effort ~M. Risk: touching every hook is exactly the Hook Source Regression pattern (`MEMORY.md`) — do it incrementally, one hook per commit, re-run the emit audit each time; never parallel-edit the shared harness (gate G4).
- **R4 (trifecta guard).** Files: new `.claude/hooks/src/trifecta-capability-guard.ts` (PreToolUse), session-state in `$TEMP/claude-trifecta-<sessionId>.json` (needs ST-02 for a correct id). Ties: composes with `file-claims`/`destructive-command-guard`; a net-new arc — propose as **SI-02** in `BACKLOG.md` if ratified. Effort ~M. Risk: false-positives blocking legitimate exfil (git push, web post) — ship in warn-mode first, tune, then enforce; reuse the interactive-vs-unattended posture from `destructive-command-guard`.
- **R5 (MCP integrity).** Files: new SessionStart/`mcp-activity-tracker`-adjacent hook; a hashes store like the blocklist. Ties: mirrors `package-install-guard`; **SI-03** candidate. Effort ~S.
- **R6 (policy layer).** Gate on **ST-06** + **ST-02**; spike first. Effort ~L. Risk: high — do not start before the permission-layer redesign lands.

## 6. Benefits

- **The 12-hook agent safety/verification chain actually fires — and stops drifting.** R1 gives the user real pre-spawn guards and post-spawn verification on every subagent (today: zero), on platform events that can't silently break the way the `'Agent'` matcher did twice.
- **A real prompt-injection defense.** R4 is the first thing in CCv3 that can stop the lethal-trifecta exfil path — the attack class the whole field (Willison, Meta, CaMeL, the adaptive-attack paper) now treats as the primary agent risk. the user runs headless sessions with MCP + web + private repo access; that is exactly the trifecta.
- **Faster, cheaper startup.** R2 may retire the 22–32s UPS wall for near-free (platform parallelism) and moves cheap filters out of Node cold-starts via `if`-conditions.
- **Fewer hand-rolled-parser bugs.** R3's typed harness kills the class that produced QW-05 (wrong field name) and the 7-impl id split-brain — one place to get stdin/fail-open/session-id right.
- **MCP supply-chain parity.** R5 extends the supply-chain vigilance the user already trusts from `package-install-guard` to the MCP tool surface (rug-pulls), which currently has zero coverage.
- **No wasted spend on the wrong upgrades.** Explicit SKIPs (LLM-judge guards, Colang/proxy rewrite) keep effort on native primitives + one policy layer instead of re-platforming 112 hooks.

## 7. Open questions

1. **Does the deployed Claude Code build expose `SubagentStart`/`SubagentStop`, native parallel hook exec, `updatedInput`, `if`, and `defer`?** The docs (https://code.claude.com/docs/en/hooks) describe them, but CCv3's registrations predate them. A single capability-probe hook should confirm each before R1/R2 build — this gates almost everything.
2. **Is the 22–32s UPS wall intra-hook serial spawning or a platform-version gap?** [Speculation] If the former, it's a code fix independent of ST-03; if the latter, the platform may already solve it. Measure before building ST-03.
3. **Warn-vs-enforce threshold for the trifecta guard (R4).** What counts as "untrusted content" (any WebFetch? any MCP read?) and "external send" (git push? Slack?) without so many false-positives that the user disables it? Ship warn-only, mine `.claude/logs/` for the real distribution first.
4. **Does a standalone Cedar/Rego evaluator run cheaply enough in a Windows TS hook (R6)?** Or is the `rules/*.md` prose + imperative guards the right stopping point for a single-operator system?
5. **Ordering guarantees under native parallel+dedup.** If R3 formalizes guard ordering (R7), how does that interact with the platform running matching hooks in parallel — do enforcement chains need to collapse into one composed guard?
