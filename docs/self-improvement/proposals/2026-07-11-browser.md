# Browser Automation — Next-Evolution Proposal (2026-07-11)

## 1. Where CCv3 is today

CCv3's browser automation is a five-tier stack, documented in `.claude/skills/browser-dev-cycle/SKILL.md:1-284`:

- **Tier 1** — `@playwright/mcp` for interactive navigate/click/fill, grounded exclusively in the Playwright accessibility-tree snapshot (`browser_snapshot`) rather than pixel/vision input (`.claude/skills/browser-dev-cycle/SKILL.md:77-107`).
- **Tier 1.5** — `@playwright/cli`, disk-based YAML snapshots for ~4x token savings vs. MCP streaming into context (`.claude/skills/browser-dev-cycle/SKILL.md:110-152`).
- **Tier 2** — a custom CDP CLI wrapper (`scripts/cdp.mjs`, 513 lines) using `playwright-core` `connectOverCDP` for perf timing, network resource listing, console capture, an in-house a11y audit (alt text, ARIA labels, heading hierarchy, `lang` attribute — `scripts/cdp.mjs:385-440`), and Lighthouse.
- **Tier 3** — `playwright-core` scripting for network mocking, viewport matrices, tracing (`.claude/skills/browser-dev-cycle/SKILL.md:171-188`).
- **Tier 4** — full Playwright Test runner for E2E suites and codegen (`.claude/skills/browser-dev-cycle/SKILL.md:191-207`).
- A `sentinel` agent (`.claude/agents/sentinel.md`) drives multi-role QA (login as admin/editor/viewer, RBAC checks, console-error capture, accessibility audit per page) using Tier 1 + Tier 2, with an explicit "re-snapshot on stale ref" recovery loop (`sentinel.md:111-119`) — but that recovery is manual/prompted, not automatic.
- Three tools are explicitly deprecated: Vercel's `agent-browser` CLI (Windows daemon bugs, GitHub #89/#90), Claude-in-Chrome MCP (6+ Windows 11 bugs), Puppeteer MCP (`.claude/skills/browser-dev-cycle/SKILL.md:262-270`).
- `.claude/rules/browser-automation.md` codifies the same tier table as a standing rule, and separately flags Claude-in-Chrome as fully deprecated for new work.

**No computer-use / vision-based fallback exists anywhere in the stack today.** Grounding is 100% DOM/accessibility-tree based across every tier. `docs/system-update/CURRENT-STATE.md` (the most recent full system audit, 2026-06-27) does not name browser automation as one of the system's active structural seams — it is not called out as broken, dead-wired, or a known gap, unlike hooks/agents/memory/context-bus. `docs/system-update/BACKLOG.md` has zero mentions of browser, playwright, CDP, or computer-use (verified via grep — no matches), meaning this component has not previously been flagged for remediation.

## 2. Frontier scan

**Computer-use / vision-grounded agents.** Anthropic's `computer` tool (Claude Platform docs, https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool) remains screenshot-driven pixel-coordinate control — a genuinely separate grounding mechanism from accessibility-tree snapshots, now on a newer action-set version (`computer_20251124`) with finer scroll control. Industry guidance (https://nohacks.co/blog/how-ai-agents-see-your-website) converges on a hybrid pattern: accessibility-tree-first for planning/action (compact, semantic, fast), vision reserved as a fallback for content the tree cannot represent.

**Why a11y-tree-only has real, named failure modes.** A 2026 arXiv survey, "Building Browser Agents: Architecture, Security, and Practical Solutions" (https://arxiv.org/abs/2511.19477, verified — abstract confirmed via direct fetch), argues architectural decisions (not model capability) determine production success, uses "hybrid context management combining accessibility tree snapshots with selective vision," and reports ~85% success on the WebGames benchmark vs. ~50% for prior browser agents (human baseline 95.7%). Separately, "Do GUI Agents Believe Their Eyes? Diagnosing State-Belief Reliance on Pixels versus Structure" (https://arxiv.org/abs/2607.04334, verified — abstract confirmed) finds agents systematically defer to structured/DOM state over pixel state when the two conflict, and that this preference "drives wrong actions and real task failure" in live environments — i.e., structure-only grounding isn't merely incomplete, it can actively mislead when the DOM state is stale or misleading and no vision cross-check exists. On the concrete gap classes: the accessibility tree structurally cannot see into **closed shadow roots** (confirmed pattern, e.g. https://github.com/whatwg/dom/issues/1290), has known **cross-origin iframe** visibility gaps, and exposes nothing for **canvas-rendered UI** unless the app author manually wires ARIA live regions.

**Self-healing selectors — this is the one live, verifiable frontier shift.** Playwright itself now ships three official **Test Agents** — Planner, Generator, and **Healer** (https://playwright.dev/docs/test-agents, confirmed via WebSearch against multiple independent 2026 sources including dev.to/playwright and testdino.com). The Healer "watches failing tests, diagnoses the cause, checks the UI at runtime, locates substitute selectors when elements change, and either fixes the test or files a bug" — built on Playwright MCP and the same accessibility-tree snapshot mechanism CCv3 already uses (no pixel-matching). This is upstream, in the exact dependency CCv3 already pins, not a new framework to adopt. [Speculation: I could not independently verify a specific numeric success rate for the Healer agent from a primary source — earlier drafts of this research cited "75%+" but that figure traces to secondary blog coverage, not Playwright's own docs, so it is dropped here rather than asserted.]

**Stagehand v3** (Browserbase, Feb 2026, https://www.browserbase.com/blog/stagehand-v3, confirmed via direct fetch) rewrote to talk to Chrome directly over CDP instead of through Playwright, reporting ~44% faster interaction on iframe/shadow-root-heavy pages, plus a "self-healing execution layer" that adapts when DOM/layout shifts, and action caching that skips repeat LLM calls on stable pages. Notably, Stagehand migrated *to* the Chrome accessibility tree for reliability — i.e., it converged on the same grounding choice CCv3 already made, not away from it.

**Benchmarks.** Live leaderboards (Steel.dev, https://leaderboard.steel.dev/leaderboards/webarena/ and /online-mind2web/) put current WebArena SOTA around ~74% and Online-Mind2Web around ~97% for top hosted agents as of mid-2026 — cite as point-in-time snapshots only, these move continuously. A newer benchmark framework, WebChallenger (https://arxiv.org/abs/2606.10423, verified — abstract confirmed), explicitly targets *reliability and efficiency* rather than raw success rate as the next evaluation axis, using a structured "PageMem" DOM representation; it reports WebArena 56.3% / Online-Mind2Web 51.0% with open-weight models, "approaching frontier proprietary systems at a fraction of the cost" — signalling the field's framing is shifting from "can it complete the task" to "how reliably and cheaply."

**Landscape context.** OpenAI's standalone agentic browser, ChatGPT Atlas, launched Oct 2025 and is being sunset as of July 2026, with agentic-browsing features redistributed into a Chrome extension and the ChatGPT desktop app rather than kept as a dedicated browser (TechCrunch, https://techcrunch.com/2026/07/09/openai-is-shutting-down-atlas-but-its-ai-browser-ambitions-are-still-growing/, confirmed via direct fetch); OpenAI's earlier "Operator" was shut down in 2025. Google's Project Mariner remains a gated research prototype. The pattern across 2025-2026: standalone "full autonomous browser" products have struggled, while the DOM/a11y-tree-first developer-SDK lane (Playwright, Playwright MCP, Stagehand, Skyvern) is the more durable, production-proven approach — which is where CCv3 already sits.

## 3. Gap analysis

**Where CCv3 is already at the frontier:** the core architectural bet — accessibility-tree-first grounding, not vision-first — is exactly what the 2026 literature (nohacks.co, arXiv 2511.19477) and the two most-cited agent SDKs (Playwright MCP, Stagehand v3) converged on. The five-tier escalation model (interactive → token-efficient CLI → perf/CDP → scripted → formal E2E) has no obvious frontier counterpart doing something structurally different; it is closer to a superset than a subset of what Stagehand/Skyvern offer. The Tier 1.5 disk-based-snapshot token-efficiency rationale is independently validated by 2026 coverage citing ~4x token reduction for CLI vs. MCP-protocol browsing.

**Where CCv3 is behind:** two concrete points.
1. **No automatic stale-ref recovery.** `sentinel.md:111-119` documents re-snapshot-and-retry as a *manual* recovery pattern the agent must invoke; there's no cached-selector-plus-DOM-diff healing loop like Stagehand v3's or Playwright's own Healer agent. Given CCv3 already depends on `@playwright/mcp`, and Playwright's Healer agent is now a first-party capability of the same upstream project, this may already be available "for free" — unverified whether the CCv3-pinned Playwright/MCP version includes Test Agents, or whether they're wired into any CCv3 workflow.
2. **No vision fallback for a11y-tree-blind content.** CCv3 has zero path today for canvas-rendered UI (chart-heavy dashboards, some rich editors), closed-shadow-DOM web components, or cross-origin iframes — all confirmed failure classes for pure a11y-tree grounding. Today the failure mode is likely a silent miss (element simply doesn't appear in the snapshot) rather than a graceful escalation to `browser_take_screenshot` + `computer`-tool-style visual grounding.

**Where CCv3 is arguably ahead or matched:** the CDP CLI (`scripts/cdp.mjs`) bundles perf/a11y/lighthouse/network into one stateless, no-external-dependency wrapper that several competing SDKs (Stagehand, Skyvern) don't offer as a first-class primitive — those are testing/interaction-focused, not perf-profiling-focused.

## 4. Recommendations

- **WATCH — Playwright Test Agents (Planner/Generator/Healer) as an upstream self-healing path.** Do not build a custom self-healing layer. Instead, verify whether the currently-pinned `@playwright/mcp` version exposes Test Agents / Healer, and if so, pilot the Healer agent on one flaky/brittle sentinel QA flow before wiring it broadly. Rationale: this is upstream in a dependency CCv3 already trusts, avoids adding a second automation SDK (Stagehand) with its own maintenance surface, and directly targets the one gap (stale-ref recovery) that's concretely worse than the frontier today.
- **WATCH — vision fallback for a11y-tree-blind content.** Not urgent: no known CCv3 workflow currently targets canvas-heavy dashboards, closed-shadow-DOM components, or cross-origin iframes, so the gap is theoretical until a project surfaces it. Track as a documented limitation; revisit as ADOPT if a real project (e.g. a canvas-based chart tool, a Workbook feature) hits it.
- **SKIP — Stagehand / Skyvern as a wholesale framework adoption.** Both externalize what CCv3 already does in-house via Playwright MCP + custom tiers, at the cost of vendor lock-in and (for Browserbase-hosted Stagehand) a hosted-infra dependency. CCv3's existing stack already reflects the same core design choices (a11y-tree grounding, self-healing direction) these frameworks converged on independently — adopting them wholesale would be a lateral move, not an upgrade, for meaningful integration cost.
- **SKIP — Anthropic `computer` tool as a primary grounding mechanism.** The frontier consensus (and CCv3's own existing design) treats vision as a fallback, not a primary grounding strategy. Full computer-use adoption would be a step backward from the more reliable, cheaper, faster a11y-tree-first approach for the vast majority of CCv3's browser tasks.
- **SKIP — chasing live benchmark leaderboard rank.** WebArena/Online-Mind2Web scores move continuously and measure hosted, single-purpose agent products (Browser Use Cloud, etc.), not developer-harness tooling like CCv3's. Not an actionable signal for this component.

## 5. Integration approach

For the one WATCH item worth near-term investigation (Playwright Test Agents / Healer):
- **Files:** `.claude/skills/browser-dev-cycle/SKILL.md` (add a "Tier 1 self-healing" subsection once verified), `package.json`/lockfile (confirm `@playwright/mcp` version), `.claude/agents/sentinel.md` (candidate first consumer — QA flows are exactly where stale-ref recovery pays off most).
- **Effort:** small — a version check + a single-flow pilot, not a new subsystem. No BACKLOG.md item currently exists for browser automation; if the pilot confirms value, it should be filed as a new low-tier BACKLOG entry rather than folded into an existing arc (ST-01 through ST-08 and SG-* items are unrelated to browser automation per the grep above).
- **Risk:** low. Playwright Test Agents run through the same accessibility-tree mechanism already in use — no new grounding strategy, no new trust boundary. The main risk is scope creep if "self-healing" is generalized beyond QA/E2E flows into interactive Tier 1 usage where a silent auto-fix could paper over a genuine UI regression instead of surfacing it.
- **What could go wrong:** if the Healer agent's auto-fix logic silently "fixes" a test that should have failed (e.g., papers over an actual accessibility regression by finding a different, less-accessible selector), sentinel's QA reports could give false confidence. Any pilot should compare Healer-modified test outcomes against a human review, not trust them blind — consistent with RULES.md's "external verification, never trust agent claims alone."

## 6. Benefits

- If Test Agents/Healer are already available in the pinned Playwright/MCP version: near-zero-cost reduction in the "stale ref, re-snapshot, retry" friction that currently requires a manual recovery loop (`sentinel.md:111-119`) — fewer failed sentinel runs, less babysitting of long QA flows.
- Documenting the vision-fallback gap (even without building it yet) gives the user a clear answer the next time a project needs to automate a canvas-heavy or web-component-heavy surface, instead of hitting a silent failure and debugging from scratch.
- Confirms the existing five-tier investment is sound — no rip-and-replace needed, which is itself a valuable (if less exciting) finding: engineering time is better spent elsewhere this cycle.
