# Memory — Next-Evolution Proposal (2026-06-30)

## 1. Where CCv3 is today (verified against the repo)

CCv3 memory is a single-tier semantic store: `archival_memory` (Postgres + pgvector, BGE-large-en-v1.5 1024-dim) queried by hybrid Reciprocal-Rank-Fusion. The substrate is sound; the periphery is partly dormant. Verified facts:

- **Hybrid RRF fusion is real and rank-based.** `search_learnings_hybrid_rrf` fuses FTS + vector by `1/(k+rank_fts) + 1/(k+rank_vector)` (`opc/scripts/core/recall_learnings.py:770`), gates vector junk with `VECTOR_MIN_COSINE` (`:883`), then applies decay (`:942`). This is exactly the rank-fusion design the frontier endorses (see §2).
- **The `plainto_tsquery` AND-bug is already FIXED.** QW-06 shipped 2026-06-28 (`websearch_to_tsquery` + `HYBRID_FLOOR` recomputed past the decay multiplier): "FTS arm 0→50, junk 3→1" (`docs/system-update/BACKLOG.md:33`). The single biggest retrieval fix the research names is done.
- **The 24.6% XML-blob pollution is already FIXED.** QW-07 shipped a `<task-notification>` machine-content guard (`isMachineGeneratedPrompt`, `memory-awareness.ts:469`; `BACKLOG.md:29`).
- **A cross-encoder reranker EXISTS but is DORMANT on the hot path.** `_apply_rerank` runs `BAAI/bge-reranker-v2-m3` with a TCP-daemon + subprocess fallback (`recall_learnings.py:1393`, model at `:1508`, candidate pool `RERANK_CANDIDATE_POOL=50` at `:1373`). But it is **opt-in `--rerank` only** (`:1873,1912,1922`), **hybrid-only** (text-only is skipped, `:1934`), and **absent from `do_recall`** — the ST-05 resident-daemon recall path has no rerank parameter (`:1587`). So neither the `memory-awareness` proactive-injection hook nor the warm daemon recall ever reranks. The hit-rate-driving surface runs unreranked.
- **Bi-temporal model + decay + supersede exist.** Rows carry `valid_from`/`valid_until`; default recall excludes superseded; `--valid-at` does point-in-time recall; decay is `exp(-age_days*0.02)` (~35-day half-life) (`.claude/skills/memory/SKILL.md:101,390-415`; `/supersede` skill). This matches the frontier bi-temporal pattern (§2) — but supersession/invalidation is **manual**, not auto-detected.
- **Resident recall daemon (ST-05) is live.** The hook routes recall through the resident BGE daemon when warm (`memory-awareness.ts:577-590`), uv subprocess fallback otherwise; warm recall ~160-250 ms vs cold ~4.7 s (`BACKLOG.md:139`, FH-02).
- **Recalled content is sanitized at injection.** `sanitizeMemoryContent` + `wrapMemoryContext` wrap results as data-only (`memory-awareness.ts:703-708`) — but only **2 of 5 injectors** route through the sanitizer; `session-start-continuity.ts` + `pre-plan-memory.ts` inject raw recall on decision-driving surfaces (`CURRENT-STATE.md:52`, the poison-then-inject seam → ST-07).
- **Write path is heuristic + append-only.** L0 quality gate blocks score-<3 noise; dedup is a fixed 0.85 cosine cut at write time; 7 enforced types (`SKILL.md:217,246-256`). No learned UPDATE/DELETE, no consolidation pass, no inter-memory links.

**Known limitations (Fable-5 review).** Hit rate **27.4%** of 281 events; **sub-agent recall 0 of 281 rows — the agent layer is memory-blind** (`CURRENT-STATE.md:35`); `agent-recall-injector` fires but yields 0-for-78 lifetime (`BACKLOG.md:63`, ST-10). The SG-01 re-baseline is data-gated on accumulating ≥50 daemon events (`BACKLOG.md:139`).

## 2. Frontier scan (last ~12 months)

**Retrieval mechanics — strong validation of our design + one clear gap.**
- Anthropic Contextual Retrieval: dense+BM25 rank fusion → cross-encoder rerank takes top-20 retrieval-failure reduction from 49% (hybrid) to **67%** (hybrid+rerank) (https://www.anthropic.com/news/contextual-retrieval). The rerank stage is the named next gain after hybrid.
- 2025 best practice = two-stage: RRF a broad pool (~top-100) for recall, cross-encoder rerank for precision; RRF-by-rank avoids the BM25-vs-cosine normalization mismatch (https://opensearch.org/blog/introducing-reciprocal-rank-fusion-hybrid-search/).
- Postgres: `plainto_tsquery` ANDs every lexeme (one rare token → zero rows); `websearch_to_tsquery` is the safe free-form parser (https://www.postgresql.org/docs/current/textsearch-controls.html) — CCv3 already applied this (QW-06).
- Each added retrieval arm raises latency/memory materially — more arms is not free (Balancing the Blend, https://arxiv.org/abs/2508.01405). GraphRAG **underperforms** vanilla RAG on lookup work: −13.4% on NaturalQuestions, ~2.3× latency, helping only multi-hop (https://arxiv.org/abs/2506.05690). LaRA: retrieval vs long-context is "no silver bullet" — keep the retriever for lookups (https://arxiv.org/abs/2502.09977). Late-interaction (ColBERTv2) rescues rare-token/short queries but at higher cost (https://arxiv.org/abs/2112.01488). Don't blanket-LLM-rewrite queries — it can degrade retrieval up to −9% via vocabulary drift; deterministically pre-normalize instead (https://arxiv.org/abs/2603.13301).

**Evaluation — the field moved from "did we retrieve it" to "did memory change the outcome."**
- ActMem: high retrieval recall does **not** guarantee the agent uses the memory — recall systematically **overstates** task performance (https://arxiv.org/abs/2603.00026).
- The field increasingly separates **coverage** from **usefulness** because they diverge: RealMem benchmarks real-world memory-driven interaction (https://arxiv.org/abs/2601.06966), while LongMemEval and ActMem (below) report retrieval recall *alongside* an answer-usefulness score rather than treating recall as the outcome. ("Mem-Helpful" in R2 is our own coinage for this split, not a named RealMem metric.)
- LongMemEval reports Recall@k/NDCG **alongside** an LLM-judge answer score, and separates offline-oracle from online recall (https://arxiv.org/abs/2410.10813). Memory-on/off ablations show large deltas (80%→45% drops when memory is removed) — the delta, not the bare hit-rate, is the headline metric.
- Memora's **FAMA** = presence-accuracy minus a staleness penalty; presence-only metrics overstate by 18–30 points and ~64% of errors come from un-forgotten stale memory (https://arxiv.org/abs/2604.20006).

**Architecture / lifecycle — where the frontier is genuinely ahead of us.**
- Four-tier taxonomy (working/episodic/semantic/procedural) × control policy (heuristic→prompted→learned); the frontier is moving toward learned control (survey, https://arxiv.org/abs/2603.07670; CoALA roots, https://arxiv.org/abs/2309.02427).
- Self-editing memory (Letta/MemGPT: the agent edits labeled memory blocks via tools, https://www.letta.com/blog/memgpt-and-letta/) and **sleep-time compute**: a background agent consolidates/dedupes/prunes during idle time (https://www.letta.com/blog/sleep-time-compute/).
- A-MEM auto-links new notes to old ones and **evolves** older notes (Zettelkasten, https://arxiv.org/abs/2502.12110). Zep/Graphiti uses bi-temporal validity windows and auto-invalidates superseded facts (https://atlan.com/know/best-ai-agent-memory-frameworks-2026/). Mem0's 2026 report flags **staleness in high-relevance memories** as explicitly unsolved by passive decay (https://mem0.ai/blog/state-of-ai-agent-memory-2026).
- Multi-agent shared memory: MIRIX routes typed memory ops across agents (https://arxiv.org/abs/2507.07957); governance (access control, write-conflict consensus) is the named blocker before un-blinding concurrent agents.
- Poisoning defense moved from per-entry write-time filtering to **cross-entry consensus + provenance + recall-time trust rerank** (A-MemGuard cuts attack success >95%, https://arxiv.org/abs/2510.02373; SSGM contradiction gate + decay, https://arxiv.org/abs/2603.11768; OWASP ASI06, https://vectorize.io/articles/ai-memory-poisoning).

## 4. Recommendations

**R1 — Wire the existing cross-encoder reranker into the hot recall path. ADOPT.**
We already paid the build cost (`_apply_rerank`, `rerank.py`, `bge-reranker-v2-m3`, daemon-aware). It's dormant exactly where it would move the 27.4% number: the proactive-injection hook and the ST-05 daemon recall both run unreranked. Wiring it (gated behind the warm rerank daemon to respect latency) is the single highest-ROI memory change available, and the frontier names rerank as **the** gain after hybrid (49%→67%, Anthropic). Risk is latency, not correctness — `_apply_rerank` already fails open to the original RRF top-K, so a cold/missing reranker degrades to today's behavior.

**R2 — Re-baseline SG-01 with a usefulness metric, not bare hit-rate. ADOPT.**
ActMem/RealMem show retrieval recall overstates task value; CCv3's 27.4% may understate or overstate real usefulness. Before optimizing the number, add a **Mem-Helpful** signal (was an injected memory subsequently `/recall`-expanded or cited in the turn?) and a periodic **memory-on/off** A/B. This is the correct SG-01 SLO and gates whether R1's lift is real. Cheap: extends existing `memory-recall.jsonl` + `/memory-stats`.

**R3 — Add a FAMA-style corpus-health SLO over the existing temporal columns. ADOPT (small).**
We already store `valid_until`; FAMA = presence-accuracy − staleness-penalty is computable from our supersede flags with no new schema. It directly instruments SG-01's "corpus-health" half and flags the frontier's named blind spot: confidently-recalled-but-stale high-relevance learnings (e.g., a corrected hook-regression entry).

**R4 — Sleep-time consolidation pass on the resident daemon. WATCH→ADOPT-lite.**
The ST-05 daemon is the natural host. A bounded idle pass that re-runs dedup over the existing corpus (write-time 0.85 dedup never re-consolidates) and proposes supersessions for contradicted entries is high-value for a flat append-only store. WATCH until R2/R3 confirm staleness is actually hurting recall; then ship as a small, read-mostly, propose-don't-delete pass (mirrors `/memory-curate`, automated).

**R5 — Auto-invalidate on detected contradiction (SSGM/Zep pattern). WATCH.**
Today supersession is manual (`/supersede`). A contradiction check at write time (does this learning contradict a high-confidence prior?) would automate what we curate by hand. WATCH — depends on R4's consolidation substrate; needs care to avoid the survey's "self-reinforcing error" failure mode.

**R6 — Recall-time trust/provenance rerank for poison defense. WATCH.**
OWASP ASI06 + A-MemGuard prescribe provenance tags (which L0–L3 layer + session produced an entry) and a trust-aware rerank at injection. This composes naturally with R1 (same rerank seam) and complements ST-07 (sanitizer coverage). WATCH until R1 lands the rerank stage; then add a trust factor to the rerank score.

**R7 — Third (entity-matching) retrieval signal. SKIP (for now).**
Mem0 fuses semantic+BM25+entity. Our 2-arm hybrid is the cheap sweet spot; "Balancing the Blend" warns each arm adds latency, and R1's reranker captures most of the precision an entity arm would. Revisit only if R1+R2 plateau.

**R8 — Knowledge-graph / GraphRAG layer over learnings. SKIP.**
GraphRAG-Bench shows it underperforms vanilla RAG on lookup workloads (−13.4%) at 2.3× latency; CCv3 recall is mostly lookup. Our flat retriever is the correct tool. Absence here is a strength, not a gap.

**R9 — RL-trained memory write policy (Memory-R1/Mem-α). SKIP/WATCH.**
Trainable ADD/UPDATE/DELETE is the research frontier, but it's heavy for a single-operator system and our write path is already gated (L0 + dedup). The cheaper R4/R5 heuristics capture most of the corpus-degradation fix. WATCH the literature; don't build.

**R10 — Full four-tier (episodic/procedural) memory + multi-agent typed routing (MIRIX). SKIP this iteration.**
Sub-agent memory-blindness is real but already owned by ST-10/ST-05; the 7 type-tags approximate semantic/procedural separation. A MIRIX-style meta-manager is a large architecture change that should wait until ST-10 proves the simpler injector path can yield anything (currently 0-for-78). Governance (MAPLE/Governed Shared Memory) would be a prerequisite and ties to the MS-* multi-session arc.

## 5. Integration approach

**R1 (reranker wiring) — primary deliverable.**
- Files: `opc/scripts/core/recall_learnings.py` (`do_recall` gains an optional `rerank: bool`, threading through `_apply_rerank` after `search_learnings_hybrid_rrf`); `.claude/hooks/src/shared/embedding-client.ts` / `embedding-daemon` to add a `rerank_ready` probe paralleling `recall_ready`; `.claude/hooks/src/memory-awareness.ts` to request rerank only when the rerank daemon is warm (same fail-open shape as the existing daemon-vs-uv branch at `:577-590`).
- Latency posture: rerank ONLY on the warm-daemon path (cold load ~50s is out of budget); pre-warm the rerank daemon at session start the same way the tldr daemon is warmed (FH-01a). Hard fail-open: `_apply_rerank` already returns the RRF top-K on any failure (`recall_learnings.py:1463,1478`).
- Ties to BACKLOG: directly serves **SG-01** (re-baseline) and depends on **ST-05** (resident daemon, shipped). Sequence after the FH-02 ≥50-daemon-event gate so the before/after is measurable.
- Effort: ~M (the model + scoring already exist; this is plumbing + a warm-up + a flag). Risk: latency creep on the warm path; mitigate with a per-call budget + the existing fail-open. What could go wrong: rerank daemon thrash under host-memory-pressure — reuse the existing `isHostMemoryPressured` gate (`memory-awareness.ts:514-520`) to skip rerank exactly as it skips the embed daemon.

**R2 (usefulness metric) + R3 (FAMA SLO).**
- Files: `.claude/hooks/src/memory-awareness.ts` (already logs `memory-recall.jsonl`; add a turn-completion correlation for Mem-Helpful), `.claude/skills/memory-stats/` (compute Mem-Recall vs Mem-Helpful + FAMA), a small `scripts/` analyzer reading `valid_until` for the staleness term. No schema change (R3 reuses temporal columns).
- Ties to BACKLOG: **SG-01** is literally "recall floor + corpus-health SLO; re-baseline the 27.4%" — R2/R3 ARE the SLO definition. Effort: ~S–M. Risk: low (read-only telemetry). What could go wrong: Mem-Helpful needs a turn-outcome signal that doesn't exist cleanly headless — start with the `/recall`-follow-up proxy already noted in `/memory-stats`.

**R4/R5 (consolidation + auto-invalidate).**
- Files: the resident daemon (ST-05) host; a new bounded idle handler that calls the existing dedup + proposes `/supersede` writes (propose-only, single-writer discipline). Ties to **ST-07** (sanitizer coverage) and the `/memory-curate` skill. Effort: M. Risk: corpus mutation — keep propose-don't-delete, audit-trail via `valid_until` (never hard-delete), guard against self-reinforcing error (survey §reflection).

**R6 (trust rerank).** Composes onto R1's rerank seam + ST-07. Effort: S once R1 lands.

## 6. Benefits (for Dave)

- **More relevant memory at the moment of work, automatically.** R1 puts a cross-encoder on the surface that injects context into every prompt — the frontier's measured path from ~49%→67% retrieval-failure reduction — using code we already wrote. Concretely: fewer "MEMORY MATCH" rows that are technically-similar-but-useless, more that actually apply.
- **An SG-01 number that means something.** R2/R3 replace a bare 27.4% hit-rate (which the literature shows can over- or under-state usefulness) with a recall-vs-usefulness split + a memory-on/off delta — so we know whether memory is earning its tokens before we spend effort tuning it.
- **A corpus that doesn't silently rot.** R3/R4 flag and consolidate stale high-confidence learnings (the named unsolved failure mode), so a corrected entry stops resurfacing as noise.
- **No wasted spend on the wrong upgrades.** Explicit SKIPs (GraphRAG, entity arm, RL write-policy, full tiering) keep us from bolting on layers the research shows hurt lookup workloads or exceed a single-operator system's payback.

## 7. Open questions

1. **Latency budget for rerank on the warm path.** Warm recall is ~160-250 ms (FH-02); a warm `bge-reranker-v2-m3` pass over 50 candidates adds how much on this Windows CPU box? Needs a measured probe before R1 ships — if it blows the hook budget, gate rerank to manual `/recall` only and keep the hook on RRF.
2. **Does R1 actually move the hit-rate, or just re-order the top-3?** Resolvable only with R2's before/after — argues for shipping R2 first or in lockstep, and respecting the FH-02 ≥50-event gate.
3. **Mem-Helpful signal in headless runs.** The `/recall`-follow-up proxy is weak for unattended sessions; is there a better cite-detection signal (e.g., the recalled `id` appearing in a later tool call)?
4. **Consolidation safety (R4/R5).** What's the contradiction-detection threshold that avoids the survey's self-reinforcing-error trap? Propose-only + `valid_until` audit trail is the floor; the auto-invalidate confidence bar is open.
5. **Is 27.4% even the right denominator?** [Speculation] If many recall fires are on prompts with no relevant prior learning, the achievable ceiling is well below 100% — the memory-on/off delta (R2) sidesteps this by measuring outcome change rather than raw hit-rate.
