## 2. Frontier scan (delta, May–July 2026; every source fetched and confirmed this session)

**Consolidation/forgetting has consolidated (sic) as the field's named open problem — not retrieval accuracy.**
- A March-2026 survey of autonomous-agent memory frames memory as a write–**manage**–read loop and names the open challenges as "continual consolidation, causally grounded retrieval, trustworthy reflection, learned forgetting" (https://arxiv.org/abs/2603.07670). CCv3 has write and read; the "manage" phase is absent.
- SleepGate ("Learning to Forget") shows retrieval accuracy "degrades log-linearly as stale associations accumulate," and a periodic consolidation/forgetting cycle restores 99.5%/97.0% accuracy at interference depths where all five baselines sit below 18% (https://arxiv.org/abs/2603.14517). The mechanism is KV-cache-specific, but the diagnosis — stale entries corrupt retrieval and passive decay alone doesn't fix it — transfers to our append-only store.
- Mem0's industry report independently names "memory staleness" and "temporal abstraction" as the hardest open problems, and now scores memory systems on a 5-dimension card (accuracy metrics + token consumption + latency) rather than accuracy alone (https://mem0.ai/blog/state-of-ai-agent-memory-2026).

**Stale-as-truth is now a benchmarked failure mode, not a hunch.**
- Momento (multi-session agentic benchmark) finds current agents "fail primarily through misestimation of user state, treating prior session history as a reliable proxy for current context rather than stale information requiring re-validation" (https://arxiv.org/abs/2606.00832). Our injected `MEMORY MATCH` blocks carry no age/freshness framing.

**Memory-poisoning defense moved to write-time provenance, with numbers.**
- SMSR is a certified defense against multi-session memory poisoning: HMAC-SHA256 provenance at write time cuts unsigned-injection attack success from 93–100% to 0%; randomized ablation + majority voting at query time holds an authenticated adversary to 8.0%; end-to-end 65.3%→5.3% (https://arxiv.org/abs/2606.12703).
- An LTM-security survey concludes memory security "cannot be retrofitted at retrieval or execution time alone, but must be anchored in storage-time provenance, versioning, and policy-aware retention" (https://arxiv.org/abs/2604.16548). This reframes ST-07 (sanitizer coverage) as necessary-but-not-sufficient.

**Reranking evidence turned against SI-01's current shape.**
- Concrete CPU numbers: BGE-Reranker-v2-m3-class cross-encoders run ≈90 ms per 100 pairs on an H100, and the same guide puts a fast consumer CPU at ~1/30th of that — back-of-envelope ~1.3s for 50 candidates, ~2.7s for 100 on CPU (https://localaimaster.com/blog/reranking-cross-encoders-guide). On a recall path that already medians ~2.3s against a 3s hard cap (§1), a synchronous 50-candidate rerank does not fit.
- MemReranker shows generic rerankers (BGE-class) do similarity matching without reasoning and specifically mishandle temporal/causal memory queries — the "have we solved this before?" shape — while a small memory-specialized reranker distilled from Qwen3-Reranker "substantially outperforms BGE-Reranker" at 10–20% of large-model latency (https://arxiv.org/abs/2605.06132). The 6/30 assumption that our dormant `bge-reranker-v2-m3` is the right model for this workload is now weaker.

**Causal structure for agent trajectories (not general GraphRAG) shows a real win.**
- AMA-Bench finds memory systems "fail to capture causal and objective information and rely heavily on lossy similarity-based retrieval"; their causality-graph agent beats the strongest baseline by 11.16 points (https://arxiv.org/abs/2602.22769). This refines — without overturning — the 6/30 "GraphRAG underperforms lookups" SKIP: the win comes from causal/temporal *relations over agent memories*, not a general graph-RAG layer.

**Harness-level memory facts (first-party).**
- Claude Code's official docs confirm the two native mechanisms — CLAUDE.md and Auto memory — both loaded at session start, with auto memory capped at "first 200 lines or 25KB" per session, per-repository, and explicitly "context, not enforced configuration" (https://code.claude.com/docs/en/memory). Our pgvector store remains the deeper layer; the native cap is an operational bound on `MEMORY.md`.
- **Flagged as unverifiable:** a third-party blog claims an unannounced "Auto Dream" background memory-consolidation feature in Claude Code (claudefa.st). Zero corroboration in the official docs or the changelog through build 2.1.207 / 2026-07-08 — do not build against it; re-check occasionally.

## 4. Recommendations

**R1 — Fix the daemon-recall routing/timeout defect. ADOPT (do first).**
89 of 184 ready-daemon recalls fell to the ~12s uv path; 28 of those injected nothing at all while a warm daemon sat idle (§1). Concretely: instrument `recallViaDaemon` failures with a reason code (timeout vs transport vs ok:false), then either raise `DEFAULT_RECALL_TIMEOUT_MS` (3000 → ~6000; `embedding-client.ts:139`) and/or find why daemon recall medians ~2.3s against a ~136ms design target (candidate: the daemon-side 2.5s query cap plus queueing on the single-threaded loop). This is a small change on an already-instrumented seam, and it is worth more today than any new capability: it converts ~89 slow-or-empty recalls into fast hits. Fail-open behavior is already correct — only the budget/diagnosis is wrong.

**R2 — Run the SG-01 re-baseline NOW; the data gate is met. ADOPT.**
87 `recall_via:daemon` events ≥ the 50-event threshold (`NEXT-SESSION-PLAN.md:54-59`). Record the new baseline (57.6% raw; per-path splits; the routing-defect rate as a tracked number), unblock ST-03/ST-10 per the plan, and add the 6/30 R2 usefulness signal (Mem-Helpful proxy) in the same pass so the R1 fix has a before/after. Re-baselining after R1 lands, on the same log, closes FH-02.

**R3 — Reshape SI-01: rerank goes async/manual-first, small pool, model re-evaluated. ADOPT (as a modification to the ratified item).**
Two new facts undercut SI-01's current "wire rerank into the hot hook path" shape: (a) CPU cross-encoder latency ~1.3s/50 candidates (localaimaster) on a path that already medians ~2.3s against a 3s cap — synchronous rerank would push the routing defect rate UP; (b) MemReranker shows generic BGE-class rerankers specifically mishandle the temporal/causal query shape our recall serves. Revised shape: keep `--rerank` for manual `/recall` and post-hoc curation; if hook-path rerank is attempted at all, cap the pool at ~20 candidates and gate on a measured warm-latency probe; WATCH MemReranker-class small models (0.6B) as a drop-in before investing further in `bge-reranker-v2-m3` plumbing. Do not start SI-01 until R1+R2 establish the corrected baseline.

**R4 — Freshness framing on injected memories. ADOPT (small).**
Momento's stale-as-truth failure mode is directly ours: injected `MEMORY MATCH` blocks carry no age signal. Add "(stored YYYY-MM-DD; may be stale — re-verify file/flag references)" to the injection wrapper in `memory-awareness.ts` using the row's timestamp we already store. Near-zero cost, no schema change, and it operationalizes the existing SKILL guidance ("reflect what was true when written") at the exact surface where the model consumes memory.

**R5 — Expose write-layer provenance as a recall-time trust tier. ADOPT-lite; WATCH signing.**
Rows already carry `session_id`, `type`, and `confidence`; what's missing is the L0–L3-vs-manual provenance distinction surfaced at recall (SMSR/LTM-survey direction). ADOPT-lite: tag new writes with their producing layer (a `provenance` tag via the existing tags column — `store_learning.py` already takes `--tags`) and show it in injected context; WATCH full HMAC signing + randomized-ablation voting (SMSR) until there's evidence of actual poisoning pressure — for a single-operator box the threat is mostly self-inflicted (a bad auto-extraction), which the trust tier already addresses.

**R6 — Light-touch causal/temporal relation tags between memories. WATCH.**
AMA-Bench's +11pt result justifies relations like `supersedes` / `caused-by` / `refines` as row-level tags feeding retrieval — NOT a graph database. We already have the `supersedes` half (bi-temporal columns + `/supersede`). WATCH until the consolidation pass (R7) exists to populate such links automatically; hand-tagging won't happen in practice.

**R7 — Sleep-time consolidation pass on the resident daemon. WATCH→ADOPT-lite (unchanged from 6/30 R4, evidence strengthened).**
The survey names consolidation the load-bearing gap; SleepGate quantifies the stale-accumulation cost; Mem0 says staleness is unsolved industry-wide. The 6/30 shape stands: a bounded idle pass on the ST-05 daemon that re-runs dedup and *proposes* supersessions (propose-don't-delete). Trigger condition to flip to ADOPT: R2's re-baseline showing stale entries in the top-3 of live recalls.

**Re-affirmed SKIPs (from 6/30, unchanged):** general GraphRAG layer; third entity-matching retrieval arm; RL-trained write policy; full four-tier/MIRIX multi-agent memory (ST-10 must first prove the simple injector path can yield anything — still 0/611).

## 6. Benefits (for the user)

- **~90 fewer slow-or-silent recalls per ~600 prompts.** R1 turns a 12s (or empty) memory fetch back into the ~2s warm path on roughly half of daemon-ready fires — that is seconds shaved off a large fraction of prompt submissions, plus recalls that currently inject *nothing* starting to inject matches.
- **A real SG-01 number this week, not eventually.** The data gate everyone was waiting on is already met; R2 just has to run. That unblocks ST-03 (prompt-latency wall) and ST-10 (sub-agent memory) — two of the highest-leverage backlog items.
- **Not spending an M-sized effort on the wrong reranker.** R3 uses fresh CPU-latency and model-fitness evidence to shrink SI-01 before it burns a build cycle on a synchronous stage the hook path cannot afford.
- **Memories that announce their age.** R4/R5 make every injected memory carry "when, and from which layer" — directly countering the benchmarked stale-as-truth failure mode at near-zero cost.

## 7. Open questions

1. **Why does warm daemon recall median ~2.3s when the ST-05 design target was ~136ms?** Candidates: queueing behind embed requests on the single loop, the daemon-side 2.5s query cap being routinely approached (slow SQL?), or `total_elapsed_ms` including non-recall hook work. R1's reason-code telemetry answers this; the fix differs by cause (raise timeout vs. tune the query vs. split the measurement).
2. **Is the 61-completed-via-uv subset actually daemon timeouts, or a different fallback trigger?** [Speculation] The 3s-cap explanation fits the latency distribution, but only per-call failure reasons will confirm; a transport-level bug (socket errors under concurrent sessions) would need a different fix.
3. **Does the 57.6% raw hit-rate reflect usefulness?** Unchanged from 6/30 (its R2): a hit is "≥1 row returned," not "the row helped." The Mem-Helpful proxy remains undefined for headless runs.
4. **SI-01 reshape governance.** SI-01 was operator-ratified; this proposal recommends narrowing it. Does the loop's contract allow a later proposal to modify a ratified item, or does that need explicit re-ratification? Flagged for the operator.
5. **MemReranker availability.** The paper reports strong numbers, but whether 0.6B weights are released/downloadable and run acceptably on this CPU box is unverified — a 30-minute probe before any R3 hook-path decision.
