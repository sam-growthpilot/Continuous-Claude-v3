# Skills System — Next-Evolution Proposal (2026-07-07)

## 1. Where CCv3 is today

CCv3 selects skills through **two parallel mechanisms**:

**A. Native Agent Skills discovery (harness-owned).** Every installed skill's `name` + `description` is loaded into the system prompt at session start; the full `SKILL.md` is loaded only when Claude judges the skill relevant (Anthropic's documented three-stage progressive disclosure). Measured cost in this repo: **139 `SKILL.md` files, ~26.4k description chars ≈ ~6.6k tokens floor**, avg 190 chars, with **20 descriptions over 400 chars** (`ui-ux-pro-max` 808, `paper-design` 739, `example-weekly` 672, …) — measured directly this session over `.claude/skills/*/SKILL.md`. This payload is always-on and the model picks semantically from it with no keyword help.

**B. A keyword+regex activation hook (repo-owned).** `.claude/hooks/src/skill-activation-prompt.ts` (UserPromptSubmit) reads `.claude/skills/skill-rules.json` and injects a "SKILL ACTIVATION CHECK" suggestion block. It adds five things on top of native selection:
- keyword matching + regex `intentPatterns` per skill (`skill-activation-prompt.ts:399-453`);
- an LLM-validation step for ambiguous keyword hits (`skill-validation-prompt.ts:127` `shouldValidateWithLLM`, `AMBIGUOUS_KEYWORDS` set at `:41`);
- 7 hardcoded high-confidence `WORKFLOW_TRIGGERS` regexes (fix/build/commit/explore/ralph/refactor/test) that escalate to auto-invoke at ≥0.90 (`skill-activation-prompt.ts:74-120`);
- a prereq/peer skill graph resolved via `skill-router.ts` (`buildEnhancedLookupResult`, `skill-activation-prompt.ts:571-607`);
- `enforcement: 'block'` handling that can hard-require a skill before any response (`skill-activation-prompt.ts:654-666`).

**Coverage and known state:**
- `skill-rules.json` registers **59 skills + 18 agents** (verified via `node` over the file) — i.e. the hook augments only ~59 of the 139 on-disk skills; the other ~80 rely entirely on native description-based selection.
- **The 28 ghost registrations are already fixed.** `CURRENT-STATE.md:54` (dated 2026-06-27) lists "28 ghost skill registrations (26 `arscontexta-*` + 2 archived, ~85 live keywords)"; that is stale — `QW-08` (`f9cdbef`, `BACKLOG.md:32`) removed them, and I verified **0 `arscontexta-*` entries remain** in the current `skill-rules.json`.
- **Evaluation is a one-time snapshot, not a live gate.** `.claude/skills/_eval/` has `eval-harness.js`, `collision-test.js`, `eval-results.json`, `collision-results.json`; `_eval-progress.json` records phases 1-6 complete. But the collision run is timestamped **2026-03-07** and reports a **39.5% collision rate** (274/694 prompts, e.g. `debug-agent | systematic-debugging` ×19, `fix | systematic-debugging` ×12) — down from 76.1% after a March keyword cleanup, but never re-run since.
- **No closed-loop routing telemetry.** `session-activity.ts:172` `logSkill` records that the hook *fired* into a per-session activity file; nothing records whether the suggested skill was actually invoked or was the *right* one. There is no durable append-only skill-routing log analogous to `memory-recall.jsonl`. Routing accuracy is therefore unmeasurable today except by re-running the March eval set.
- **Known operational limit:** a skill-listing cap has bitten before (memory `feedback-skill-cap-check`) — the `/skills` list can silently truncate above a threshold with 200+ installs.

## 2. Frontier scan

Verification status is explicit per source. **Eight sources were re-fetched and quote-verified at primary this session** (marked ✓). Three are relayed from the `oracle` research agent and were **not** independently fetched by me (marked ⚠ relayed) — treated as supporting, never as the sole basis for a numeric claim.

1. **✓ Anthropic — "Equipping agents for the real world with Agent Skills."** `https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills` — verified quotes: "At startup, the agent pre-loads the `name` and `description` of every installed skill into its system prompt"; the full `SKILL.md` loads only "If Claude thinks the skill is relevant." Guidance for many skills is limited — keep `SKILL.md` lean, push detail into referenced files, "if certain contexts are mutually exclusive … keeping the paths separate will reduce the token usage." **There is no Anthropic-prescribed router or ceiling for hundreds of Skills** — the scale answer lives in the tool-use layer (source 3), not the Skills docs.

2. **✓ Anthropic — "Introducing advanced tool use."** `https://www.anthropic.com/engineering/advanced-tool-use` — verified figures: Tool Search = **"85% reduction in token usage while maintaining access to your full tool library"**; selection accuracy with Tool Search on rose Opus 4 **49%→74%** and Opus 4.5 **79.5%→88.1%**; Programmatic Tool Calling **43,588→27,297 tokens (37%)**; Tool Use Examples **72%→90%** on complex parameter handling.

3. **✓ Anthropic docs — "Tool search tool."** `https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool` — verified: mark tools `defer_loading: true` (up to **10,000** deferred tools/request; ≥1 non-deferred required); only names/search-tool load up front, Claude searches names+descriptions+arg names, API expands `tool_reference` blocks (≤5 by default). Verified quote: **"Claude's ability to pick the right tool degrades once you exceed 30–50 available tools"**; a 5-server setup "can consume ~55k tokens … Tool search typically reduces this by over 85 percent." Two variants — **regex** and **BM25** (keyword/natural-language, *not* embeddings by default) — but a documented **"Custom tool search implementation"** lets you return `tool_reference` blocks "using embeddings or semantic search" (cookbook recipe linked). **Critical scope note:** this mechanism is for the `tools` array. The Agent Skills description payload (source 1) has **no documented `defer_loading` equivalent** — all skill descriptions stay resident.

4. **✓ RAG-MCP.** arXiv **2505.03275** — verified abstract: semantic retrieval of the relevant tool subset before prompting "**more than triples tool selection accuracy (43.13% vs 13.62% baseline)**" and "cuts prompt tokens (e.g., by over 50%)."

5. **✓ ToolRet — "Retrieval Models Aren't Tool-Savvy."** arXiv **2503.01763** (ACL 2025 Findings) — verified abstract: a benchmark of **7.6k retrieval tasks over a 43k-tool corpus**; "even the models with strong performance in conventional IR benchmarks exhibit poor performance on ToolRet … This low retrieval quality degrades the task pass rate," fixed only with a **200k-instance training set**. (The specific "33.83 nDCG@10" figure the oracle offered is **not in the abstract** — dropped.) Lesson: off-the-shelf embeddings are *weak* on tool/skill descriptions without tuning.

6. **✓ LiveMCPBench — "Can Agents Navigate an Ocean of MCP Tools?"** arXiv **2508.01780** — verified abstract: **70 servers / 527 tools**; "while Claude-Sonnet-4 reaches **78.95% task success, most models achieve only 30-50%**"; and "**retrieval errors account for nearly half of all failures, highlighting retrieval as the dominant bottleneck**."

7. **✓ "The 99% Success Paradox."** arXiv **2605.18857** (2026) — verified: introduces **Bits-over-Random (BoR)**; "On the 20 Newsgroups dataset, BM25 and SPLADE both report >99% success at K=100 (coverage), yet BoR ≈ 0, indicating random-level selectivity." Root cause: IR was built for humans who "could scan, filter, and discard irrelevant information," but "LLMs … [lack] this filtering ability." Implication: **low-precision over-suggestion, not misses, is the real failure mode.**

8. **✓ "How Many Tools Should an LLM Agent See? A Chance-Corrected Answer."** arXiv **2605.24660** (2026) — verified: applies BoR to shortlist *depth* across registries "ranging from 20 to 3,251 tools"; "Show too many tools and the model struggles to choose. Show too few and the correct tool may not appear" — there is no universal shortlist size, and raw success rate hides whether the shortlist beat random.

9. **⚠ relayed — ScaleMCP.** arXiv **2505.06416** — gives the agent an *MCP-retrieval tool* (agent passes keywords → framework auto-loads retrieved servers), keeping retrieval *inside* the loop over ~5,000 servers. Supporting evidence for the "agent-callable search tool" pattern; not fetched by me this session.

10. **⚠ relayed — "Less is More: Optimizing Function Calling … on Edge Devices."** arXiv **2411.15399** (Nov 2024) — dynamic tool-set pruning without fine-tuning raised selection accuracy toward ~89%. Flagged: pre-window, edge/small-model-framed; supporting only.

11. **⚠ relayed — MCP tool poisoning / auto-loaded-description injection.** Invariant Labs (`https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks`) + OWASP MCP Tool Poisoning. Mechanism (widely documented): malicious instructions hidden in a tool/skill *description* act as indirect prompt injection **merely by being loaded into context — before invocation**. The specific "84.2% attack success" figure some secondary write-ups cite is **unverified at primary** and is not used here. Not fetched by me this session; mechanism is broadly corroborated.

## 3. Gap analysis

**Where CCv3 is ahead or unusual:**
- The keyword hook adds capabilities the model-driven path lacks: **`enforcement: 'block'`** (a deterministic gate the native selector cannot provide), **workflow auto-invoke**, and a **prereq/peer skill graph**. The frontier (retrieval) does not give these — they are a genuine orthogonal layer.
- **Cross-checking / ambiguity validation** (`shouldValidateWithLLM`) is a real precision defense against the exact everyday-vs-technical collision the 99% Paradox (source 7) formalizes.
- CCv3 already owns a **BGE-large embedding stack** (the memory system) that could back a client-side skill retriever *if* one were ever needed — the hard infrastructure exists.

**Where CCv3 is behind or exposed:**
- **Skills have no deferral path; the description payload is always-on.** ~6.6k tokens floor for 139 descriptions sit in every session's system prompt. Anthropic solved this *for tools* with `defer_loading` + Tool Search (85% reduction, source 3) but **has not extended it to Skills** — so CCv3 cannot simply opt in. The tool-search doc's "degrades once you exceed 30–50" (source 3) is about tools-array selection, not Skills — but the direction transfers: at 139 always-resident descriptions CCv3 is well past that knee for the model's unaided pick, and the 20 bloated descriptions (>400 chars) make both the cost and the collision surface worse.
- **The keyword hook over-suggests at low precision.** 39.5% collision rate (March snapshot) is precisely the low-precision over-suggestion sources 6 (retrieval = half of failures) and 7 (99% ≡ random) name as the dominant failure mode. It also covers only 59/139 skills, so it will never be a *coverage-complete* router — chasing that is the wrong goal.
- **No live routing telemetry.** The only accuracy measurement is a static 2026-03-07 eval run. There is no BoR-style selectivity metric and no suggested-vs-invoked log, so we cannot tell today whether the hook helps or hurts, or whether description edits improve selection.
- **Every skill description is an unaudited injection surface.** Because all 139 descriptions auto-load at discovery (source 1), a poisoned description (source 11) executes as indirect injection *before* any skill is invoked. CCv3 installs external skills (`npx skills add`, `vet-skill`) but has no description-scan gate on that path.

**Where the frontier direction does NOT fit CCv3 (yet):**
- A full RAG/embedding skill router is **premature at 139 skills**. ToolRet (source 5) shows naive embeddings *underperform* on tool/skill descriptions without a tuned training set; native selection already does semantic matching; and the always-on cost (~6.6k tokens) is real but modest. The retrieval win is large at thousands of tools (sources 4, 6, 9), not at ~139 skills.

## 5. Integration approach

**R1 — Description hygiene + recurring collision gate (effort S, risk low):**
- Files: the 20 offending `.claude/skills/*/SKILL.md` frontmatter blocks; `.claude/skills/_eval/collision-test.js` + `eval-harness.js` (already present); a wire-in from the `health-check` skill / MOT weekly cadence (Friday 8am job already exists per `health-check` skill).
- Method: for each long description, keep one crisp capability sentence + the distinguishing trigger keywords; move examples into the body (progressive disclosure, per source 1). Re-run `collision-test.js`, record the new rate into `_eval-progress.json`, and fail the weekly gate if the collision rate regresses past a band.
- Ties to BACKLOG: complements the `SG-03`/`DEL-12` cleanup arc (per-item-grep skills / stubs); independent of `ST-02`.
- What could go wrong: over-trimming a description degrades *native* selection (the thing we most rely on) — so gate every trim through the collision set before/after, and never trim below the distinguishing keywords.

**R2 — Hook reframe + routing telemetry (effort M, risk medium):**
- Files: `skill-activation-prompt.ts` (cap the number of surfaced skills per priority tier; keep block/workflow/graph paths); `session-activity.ts` (add a durable append `logSkillRouting(sessionId, suggested[], invoked?, matchType)` writing `.claude/logs/skill-routing.jsonl`); a new `memory-stats`-style reader for aggregate precision.
- Closed-loop: the "invoked" signal comes from the `Skill` tool-use event — correlate suggested (UserPromptSubmit) with invoked (subsequent Skill call) in the same session. This depends on a stable session id → **ties to `ST-02`** (canonical `getSessionId`) and the `SG-04` telemetry-joinability arc; where ST-02 is unlanded, fall back to the per-session activity file already keyed by `session_id`.
- What could go wrong: capping surfaced candidates could hide a genuinely-needed skill (the source-8 "too few" failure) — cap by *priority tier*, never drop `critical`/`block` skills; tune the cap against the R1 collision set.

**R3 — Semantic retrieval (WATCH; no build now):** documented trigger conditions only. When triggered, the client-side custom-tool-search path (source 3) backed by the existing BGE embeddings is the intended shape; ToolRet (source 5) says budget for a tuned/curated retrieval set, not raw cosine over descriptions.

**R4 — Description-scan gate (effort S, risk low):**
- Files: `skill-install-registrar.ts` and/or the `vet-skill` skill flow — add a frontmatter scan step that flags imperative/hidden-directive patterns in `description` before a new skill is registered into `skill-rules.json`.
- Ties: reuses the existing install/vet chokepoint; no new runtime surface.
- What could go wrong: false positives on legitimately imperative descriptions — make it warn-and-confirm, not hard-block, for skills the user authored.

## 6. Benefits

- **Lower always-on cost + better unaided selection (R1):** trimming the 20 bloated descriptions cuts the ~6.6k-token floor and, more importantly, raises the *precision* of the payload the model picks from every session — the lever sources 3/7/8 identify as the real one. Zero new infrastructure.
- **Routing finally becomes measurable (R2):** today a skill-rules edit is a guess; a suggested-vs-invoked log + a recurring collision gate turn the Skills System into something with a live accuracy number, the same way `memory-stats` did for recall. The hook stops over-suggesting (39.5% collisions) by capping to a high-precision shortlist.
- **The hook does only what it's uniquely good at (R2):** deterministic `block`/workflow/graph enforcement — and stops losing a coverage race against 139 skills that native semantic selection already handles.
- **A closed injection hole (R4):** external skills can no longer smuggle instructions through an auto-loaded description before anyone invokes them, at the one install chokepoint.
- **No premature spend (R3/R5):** CCv3 avoids building and tuning an embedding router that ToolRet predicts would underperform at this scale, while keeping a clear, triggered path to adopt it when skill count actually demands it.

## 7. Open questions

1. Will Anthropic extend `defer_loading` / Tool Search to **Agent Skills** (not just the tools array)? If yes, R3 flips from WATCH to a near-free adopt and the ~6.6k floor largely disappears — worth tracking the Skills docs and changelog.
2. What is the right **surfaced-candidate cap** for R2 given no current BoR measurement — is a per-tier cap of ~3 defensible, or should the cap be learned from the R1 collision set once telemetry (R2) exists? (Chicken-and-egg: telemetry must land before the cap can be tuned empirically.)
3. Does the harness's **skill-listing cap** (memory `feedback-skill-cap-check`) silently truncate the native description list at 139 skills today? If so, some skills may already be invisible to native selection — which would raise R1/R3 priority. Needs a direct check of the live `/skills` surface.
4. Of the ~80 skills *not* in `skill-rules.json`, how many are ever invoked? R2's telemetry would answer this — and low/zero-use skills are `DEL`-arc archive candidates (fewer skills → higher native precision, the cheapest scale fix of all).
5. Is the 2026-03-07 collision set still representative of current prompt patterns, or should R1 rebuild `eval-sets.json` from recent real prompts before re-running the gate?
