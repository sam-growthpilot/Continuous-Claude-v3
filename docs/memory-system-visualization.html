System at a glance
Five pillars. Every Claude session has these running underneath: postgres+pgvector hook store embed daemon reranker (opt-in). The hook is the only auto-trigger; everything else is on-demand.

What runs without you asking

  • UserPromptSubmit fires memory-awareness.ts on every message
  • Hook auto-spawns BGE daemon if none alive (lockfile-protected)
  • Recent matches are injected as MEMORY MATCH (N results)
  • Telemetry written to .claude/logs/memory-recall.jsonl

What you trigger explicitly

  • recall_learnings.py --query "..." — ad-hoc semantic search
  • store_learning.py via /remember skill — manual ingest
  • --rerank flag — opt-in cross-encoder for high-stakes queries
  • --text-only / --vector-only — bypass hybrid for debugging

02 · Write Path

From an insight to a row in archival_memory.

A learning enters through store_learning.py. The L0 quality gate filters noise. The BGE daemon turns the body into a 1024-dim vector. A dedup check against existing entries at 0.85 cosine prevents duplicates. Only then does the row land.

Store flow (write)

Either explicit (you run /remember) or auto-extracted by the L0 hook from notable tool-use patterns. Each store includes type, content, context, tags, confidence.

Parses flags (--session-id, --type, --content, --context, --tags, --confidence), loads .env with DATABASE_URL, acquires an asyncpg pool.

Rejects: NOISE prefix tokens, too-short content, bad newline ratios. Returns {passes: bool, reason: str}. The docs historically said "score < 3" — that's drift; the gate is binary.

03 · Write Path

L0 quality gate — the noise filter.

Auto-extracted learnings from hooks get filtered here before they ever reach pgvector. The gate is boolean — pass / fail — not a numeric score, despite older docs claiming otherwise. Reasons are surfaced for blocked entries so future runs can adjust.

Examples that PASS

WORKING_SOLUTION: "Bug A fixed in rerank.py:485 — ping_daemon timeout 0.2s → 1.5s mirrors embedding-client.ts pattern. NDCG +107% reconfirmed."
ARCHITECTURAL_DECISION: "Mode-aware floor split: HYBRID_FLOOR=0.01 for RRF scores, TEXT_ONLY_FLOOR=0.05 for ts_rank. Selected at runtime by daemonReady."
FAILED_APPROACH: "Mass-killing python.exe to clean orphans killed the rerank daemon mid-eval. Always check PID against discovery file first."

Examples that BLOCK

NOISE prefix: "TODO: figure out later" → blocked (begins with noise token)
Too short: "fixed it" → blocked (below min length)
Wall of newlines: "stack\n\n\n\n\ntrace\n\n\n…" → blocked (newline ratio > threshold)
Already exists: cosine ≥ 0.85 against an existing row → dedupe (no new insert)

The gate, in code

# opc/scripts/core/store_learning.py:195 def validate_learning_quality(content: str) -> dict: if starts_with_noise_prefix(content): return {"passes": False, "reason": "noise_prefix"} if len(content) < MIN_CONTENT_LEN: return {"passes": False, "reason": "too_short"} if newline_ratio(content) > MAX_NEWLINE_RATIO: return {"passes": False, "reason": "high_newline_ratio"} return {"passes": True}
Doc drift caught in audit. RULES.md / CLAUDE.md / SKILL.md described this as "NOISE entries score < 3 and are blocked." No such score exists. Tracked in memory-system-audit-followup-2026-05-21.md; P1 cleanup pending.

04 · Read Path

From a prompt to MEMORY MATCH in context.

Every UserPromptSubmit fires memory-awareness.ts. The hook pings the daemon, spawns a recall subprocess, merges local + DB candidates, applies a mode-aware floor, and injects the matches as system context. Target latency: under 2 s warm.

Recall flow (read)

User prompt fires UserPromptSubmit hook

Hook receives stdin JSON with the user's text. First checks: is it long enough to be memory-relevant? Is it a slash command (skip)? Is this a subagent invocation (skip)?

Intent extraction + git-query expansion

Pulls the first ~150 chars as the search intent. If the prompt references a path or branch, expands the query with that context. Cheap string ops, < 5 ms.

Reads the discovery file, sends a {"op":"ping"} frame. If reply has status:"ok" within 1.5 s → daemon is alive and the path goes hybrid. Otherwise → falls back to --text-only.

One SQL query, two CTEs (FTS rank + vector rank), Reciprocal Rank Fusion combines them. Uses GIN index for FTS and IVFFlat for vectors. Scope-filtered to project + global. Returns top k × 2 candidates.

05 · Engines

BGE embedding daemon — long-lived vector service.

BAAI/bge-large-en-v1.5 loaded once (~35 s warm pagecache, longer cold), then serves 1024-dim embeddings over TCP loopback at ~50–150 ms per call. Supervisor + worker process pair. Lockfile mutex prevents double-spawn. Heart of the hot path.

Daemon lifecycle

Why supervisor + worker?

Python's --daemon flag forks twice. PID #1 is the supervisor (parent), PID #2 is the worker (child that actually serves TCP). Yesterday the audit briefly flagged this as an "orphan" race; today we know it's the standard double-fork pattern. Don't kill either one expecting "cleanup" — they're a pair.

Why a lockfile?

Two Claude Code sessions hitting the hook simultaneously could each try to spawn. embedding-client.ts writes $TEMP/ccv3-embedding-spawn.lock with a 60 s TTL; second spawner observes it and waits. Combined with the daemon-side _check_existing_daemon guard (commit 7c95ca5), the common race is closed.

Ping protocol — what travels over TCP

// embedding-client.ts:74 const DEFAULT_PING_TIMEOUT_MS = 1500; // matches Python side after audit P0 fix #1 // Sent over framed TCP (length-prefixed JSON): { "op": "ping" } ↓ { "status": "ok", "model": "BAAI/bge-large-en-v1.5", "dim": 1024 } # Embed (recall_learnings.py side): { "op": "embed", "text": "how do I debug a hook?" } ↓ { "status": "ok", "vector": [0.043, -0.012, ... 1024 values] }

06 · Engines

BGE reranker — opt-in stage-2 cross-encoder.

BAAI/bge-reranker-v2-m3 is a cross-encoder: it scores the (query, candidate) pair jointly rather than embedding each independently. Higher quality, much higher cost. Default OFF; the hook never calls it. Reserved for high-stakes ad-hoc queries via --rerank.

Why opt-in?

The 42-pair eval (clean run after Bug A fix) showed NDCG@5 jumping from 0.385 baseline → 0.798 reranked. +107 % quality lift. But the eval-harness wall-clock p95 was 35 s (subprocess startup + cross-encoder forward pass). Production hook gate is 500 ms p95. The math doesn't work for default-on yet.

Pre-condition for default-on: faster reranker (smaller model / ONNX quantization / GPU) AND in-process recall pipeline (no subprocess overhead). Neither is in current scope.

Hook never calls --rerank. Grep memory-awareness.ts for rerank: zero matches. This entire engine is for direct CLI use (recall_learnings.py --rerank --query "...") when you want maximum quality and can accept multi-second latency.

07 · Behavior

Four recall modes, two floors, one fusion.

Hybrid is the default. Text-only is the fallback when the daemon is unreachable. Vector-only is for debugging the vector arm in isolation. Rerank stacks on top. Each mode has its own score scale and its own floor for filtering out noise.

Hybrid RRF

default

FTS + vector ranks, fused via Reciprocal Rank Fusion.

Floor: HYBRID_FLOOR = 0.01

Score range: ~0.01 – 0.03

Used by: the hook (always)

Text-only

--text-only

Postgres FTS via ts_rank. Skips the daemon entirely.

Floor: TEXT_ONLY_FLOOR = 0.05

Score range: ~0.05 – 0.5

Used by: hook fallback + debugging

Vector-only

--vector-only

pgvector cosine similarity over BGE-large embeddings.

Floor: --threshold raw (default 0.2)

Score range: 0 – 1 (cosine)

Used by: rarely — fairness eval

Hybrid + Rerank

--rerank

Hybrid retrieves top 50, cross-encoder re-orders.

Floor: applied pre-rerank only

Score range: rerank logit (post-sigmoid)

Used by: opt-in high-stakes queries

Reciprocal Rank Fusion — the formula

-- recall_learnings.py builds this as SQL CTEs WITH text_ranked AS ( SELECT id, ts_rank(fts_vector, query) AS r, ROW_NUMBER() OVER (ORDER BY r DESC) AS rank_text FROM archival_memory WHERE fts_vector @@ query ), vec_ranked AS ( SELECT id, 1 - (embedding <=> query_vec) AS cos, ROW_NUMBER() OVER (ORDER BY cos DESC) AS rank_vec FROM archival_memory ) SELECT id, 1.0/(60 + rank_text) + 1.0/(60 + rank_vec) AS rrf_score FROM text_ranked FULL JOIN vec_ranked USING (id) ORDER BY rrf_score DESC;

k = 60 is the standard RRF constant. The sum is small (~0.016 max when both ranks are #1), which is why HYBRID_FLOOR is set at 0.01 not 0.5.

Why two floors? Score scales differ.

A floor of 0.05 makes sense for ts_rank scores (which cluster 0.05–0.5). It would discard EVERYTHING from the RRF mode. Mode-aware floor split lets each mode use a sensible threshold.

ts_rank
0.05 – 0.5
RRF
0.01 – 0.03
cosine
0 – 1

Red line on each bar = floor cutoff. Anything left of the line gets filtered.

08 · Behavior

Every hook fire leaves a trace.

memory-recall.jsonl appends one line per UserPromptSubmit. Schema is fixed; fail-open writes (errors never break the hook). This is the single source of truth for "did the memory system actually help?"

A real jsonl entry, annotated

{ timestamp "2026-05-21T13:51:41.383Z", session_id "68c6363b-9c60-449d-963f-23f610410691", intent "how do I debug a hook?", mode "hybrid", daemon_ready true, floor_applied 0.01, top_score 0.016, kept_after_floor 3, results_count 3, source "merged", total_elapsed_ms 967, db_subprocess_timed_out false }

Healthy signatures

  • daemon_ready: true
  • mode: "hybrid"
  • kept_after_floor > 0 on memory-relevant prompts
  • total_elapsed_ms < 5000
  • db_subprocess_timed_out: false
  • source: "merged" or "db" or "local"

Degradation signatures

  • db_subprocess_timed_out: true rate > 20 %
  • daemon_ready: false + mode: "text-only"
  • kept_after_floor: 0 sustained over many entries
  • source: "empty" on prompts that should have hit
  • total_elapsed_ms ≥ 12000 (SIGKILL ceiling)

What about extraction telemetry?

A separate stream — .claude/logs/agent-recall.jsonl — captures agent-side recall injection (PostToolUse hook from agent-recall-injector.ts). Today it's effectively dormant (1 entry total). Worth a check if you start delegating to agents heavily.

How to read your own telemetry

# Last 5 hook fires: tail -n 5 .claude/logs/memory-recall.jsonl | jq '{ts, mode, kept_after_floor, total_elapsed_ms}' # Hit rate over last 50 entries: tail -n 50 .claude/logs/memory-recall.jsonl | jq -s 'map(select(.kept_after_floor > 0)) | length / 50 * 100' # Or use the canonical skill: /memory-stats

When things break, where they show up, and how to recover.

The host-RAM defense gap (BLOCKER B1, filed)

The audit identified this as a real architectural BLOCKER, but the synthesis chose CONDITIONAL GO because the P0 ping-timeout fix (recall_learnings.py:226, 0.2 s → 1.5 s) removes the primary trigger — the asymmetry that turned slow embeds into SIGKILLs.

Residual sensitivity: if free RAM drops below ~2 GB, the BGE-large model gets paged to pagefile.sys and embedding calls slow ~10× until it refaults. The cleanest permanent fix is a free-RAM probe at hook entry + fallback to text-only when pressure is detected.

Filed as P2 in docs/memory-system-audit-followup-2026-05-21.md with explicit trigger conditions and a tested recovery runbook.
